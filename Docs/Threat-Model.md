# Threat model: current prototype

## Scope and trust boundaries

Archx supplies request signals and rate-limit decisions; a host, not Archx, must authenticate users and authorize operations separately and must enforce the decision before executing a protected action. The C core and Python policy service are distinct implementations. The browser encrypts caller-provided signals; it cannot collect Linux hardware IDs. Supported deployment is not yet established; the demo HTTP server and WSGI development example are private experiments, not production entrypoints. Native Windows/macOS and distributed enforcement are **not implemented**.

Assets include service availability, rate-limit and replay state, host operations, pseudonymous device/IP records, raw identifiers during processing, and the HMAC and sealed-transport private keys. Attackers may control their client, browser, submitted identifiers, IPs/proxies and traffic timing; may replay an observed encrypted request; and may try to exhaust stores or workers. Trusted boundaries are the host's authentication/authorization and decision enforcement, the configured trusted proxy and restricted origin, secure storage, independent trusted client code and server public key delivery, and TLS. A compromised host, key, proxy or same-page script is outside prototype protection. Clients do not have to tell the truth; a signal is neither authentication nor proof of a unique person or device.

## Threats, evidence and outstanding limitations

Every listed threat links a targeted synthetic regression; some tests deliberately demonstrate an attack or limitation rather than a mitigation. A linked test proves only its assertions, not complete protection. “Known limitation” records a residual risk; it does **not** imply maintainer or operator acceptance. Operators need their own threat model, access policies, response and human recovery procedures. The table is an inventory, not a complete security audit.

| ID | Threat | Regression or known limitation | Response and remaining work |
| --- | --- | --- | --- |
| T01 | Forgery, cloning, or rotation of all signals and IP | [`test_fabrication_and_replay_remain_possible`](../tests/test_demo.py) exercises fabricated signals; [`attack_lab.py`](../tools/attack_lab.py) demonstrates rotation. **Known limitation:** there is no source authenticity or guaranteed uniqueness. | Independent host authentication/authorization and other abuse controls; do not use fingerprints as credentials. |
| T02 | Victim poisoning with forged identifiers | [`test_forged_signal_can_exhaust_victim_bucket`](../tests/test_demo.py) demonstrates victim denial; verification does not prove device ownership. | Host-controlled remediation and recovery; avoid sole reliance on self-reported signals. |
| T03 | Shared NAT causes collateral denial | [`test_shared_ip_warning`](../tests/test_demo.py) demonstrates unrelated clients sharing a limit. | Review thresholds and provide human recovery. Separate thresholds do not eliminate collateral denials or the need for recovery. |
| T04 | C bucket churn evicts active quota | [`main`](../tests/test_core.c) fills the store, churns keys and checks an exhausted bucket, including parallel admission. **Known limitation:** saturation can deny new keys indefinitely; no automatic reclamation. | Authorized targeted `ax_reset` changes that key's enforcement; full restart loses all state. |
| T05 | Exhaustion of Python state | [`test_capacity_closed`](../tests/test_demo.py) and [`test_capacity_fail_closed`](../tests/test_sqlite_engine.py) check bounded denial. **Known limitation:** expiry backlog denies requests until drained; idle cleanup is optional and not automatically started. | Capacity monitoring and safe operational recovery remain incomplete; memory restart resets quotas. |
| T06 | CPU, worker, socket or challenge flooding | [`test_many_slow_connections_cannot_exceed_worker_limit`](../tests/test_boundaries.py) tests one process with synthetic clients. **Known limitation:** stalled application code, kernel/upstream queues, multiple processes and a supported host are not bounded. | Do not expose the demo; bounded host integration and overload controls are release blockers. |
| T07 | Replay or intercepted first submission | [`test_single_use_expiry_peer_and_capacity`](../tests/test_replay.py) tests single use and expiry. **Known limitation:** first arrival wins; sealed boxes do not authenticate sender and fresh fabricated payloads remain possible. | TLS and independently trusted code/key delivery; isolate origin. Shared multi-host replay is not implemented. |
| T08 | Spoofed forwarded client IP | [`test_trust_boundary_and_header_validation`](../tests/test_proxy.py) tests single-proxy parsing; [`test_same_service_user_can_bypass_proxy`](../tests/test_https_wsgi_unix.py) demonstrates same-UID bypass in an experimental TLS/Unix-socket topology. **Known limitation:** these are not a supported isolated origin or a production trust boundary. | Restrict direct origin and trust only an explicitly configured sanitizing proxy; local UID, filesystem and ingress isolation require a reviewed deployment design. |
| T09 | Secret or database disclosure and tracking | [`test_no_raw_request_data_stored`](../tests/test_sqlite_engine.py) checks a synthetic default-mode database dump. **Known limitation:** HMACs are linkable; raw IP mode, transient values, logs, WAL, backups and other infrastructure require separate controls. | Restrict access and minimize retention; tested key rotation and deletion procedures remain open. |
| T10 | Provider outage or reputation false positives | [`test_feed_refresh_cache_staleness_and_failed_update`](../tests/test_security.py) and [`test_turnstile_verification`](../tests/test_security.py) use fake providers. **Known limitation:** live Turnstile behavior and feed accuracy are not validated. | Choose failure/stale policies, monitor and provide recovery; staging remains open. |
| T11 | State loss, configuration mismatch or rollback | [`test_wrong_secret_and_policy_fail_closed`](../tests/test_sqlite_engine.py) and [`test_missing_schema_objects_are_not_silently_recreated`](../tests/test_sqlite_engine.py) cover limited cases. **Known limitation:** deletion, older restores, runtime tampering, memory restarts and missing replay marker plus table can still reset or revive state. | Migration, rollback-resistant recovery, durable backups and comprehensive fault injection remain open. |
| T12 | Compromised browser scripts or replaced key | [`test_substituted_public_key_exposes_sealed_payload`](../tests/test_security.py) demonstrates that an attacker-supplied public key lets the attacker decrypt a synthetic payload while the intended recipient cannot. **Known limitation:** encryption trusts supplied key and executing code; TLS and sealed payloads do not secure a malicious client. | Independently authenticate public key and client delivery; protect build and third-party scripts. |
| T13 | Clock changes or delays alter quotas and replay expiry | [`test_sqlite_valid_request_wait`](../tests/test_state_clock.py) and [`test_sqlite_challenge_consume_wait`](../tests/test_replay.py) exercise synthetic lock waits. **Known limitation:** wall-clock jumps and restored state are not rollback resistant. | Design and verify a persistent clock/recovery strategy; do not claim no-silent-reset. |

No test establishes protection against every attack, a real person's uniqueness, or production fitness. The [next-version tracker](Plan/Next-Version.md) contains remaining required mitigations and evidence gates. The owner enabled GitHub private vulnerability reporting; see [SECURITY.md](../SECURITY.md) for the reporting link and the untested end-to-end notification flow. This inventory does not constitute formal acceptance of residual risks or an independent security review.
