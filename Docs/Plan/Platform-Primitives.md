# ADR: experimental native store clock and mutex

## Decision and scope

The internal `src/platform.h` contract initially covers OS randomness, an exclusive non-recursive mutex and an arbitrary-origin millisecond interval clock for the C token-bucket store. It is **not** a complete platform abstraction: collection, private persistence, file locking, architecture, error translation, TLS, address parsing and library loading remain open. The full C core, collectors, fallback identity, CLI and Python/Node bindings remain Linux-only. A successful primitive test on another OS is not product support or native collector evidence.

The clock policy preserves current Linux behavior: system suspend is intended **not** to refill tokens. Linux uses `clock_gettime(CLOCK_MONOTONIC)` (`<time.h>`); macOS uses `clock_gettime(CLOCK_UPTIME_RAW)` (`<time.h>`); Windows uses `QueryUnbiasedInterruptTime` (`<windows.h>`, `<realtimeapiset.h>`), converting 100-nanosecond units to milliseconds. macOS and Windows are proposed adapters only; minimum OS versions, distribution permissions and actual sleep/resume behavior require native testing. The clocks have arbitrary origins and must not be used as UTC, durable timestamps, cross-machine synchronization or identity. Windows QPC includes sleep according to Microsoft, so it was rejected here to preserve the selected policy. Windows' unbiased clock may have coarse resolution; tests must not assume every read advances.

Linux/macOS use dynamically initialized `pthread_mutex_t` (`<pthread.h>`); Windows uses an exclusive SRW lock (`<windows.h>`, `<synchapi.h>` via the Windows SDK). Locks cannot be copied, recursively acquired, or destroyed while in use. Initialization, lock and time-read errors fail the C limiter closed; no bucket is inserted or charged on a failed time read. If unlock reports failure, a mutation may already have happened; `ax_check` returns a denial with an error and `ax_reset` returns `AX_ERR_INTERNAL`, **not** a transactional rollback. Existing buckets are not silently evicted. The current public ABI is not broadened to claim portable collections.

## OS randomness

The internal contract requests at most 256 bytes and requires callers to discard all output on failure; a zero-length request is a no-op. Linux now uses `getrandom(..., GRND_NONBLOCK)` (`<sys/random.h>`): it retries interruptions/short reads but returns failure if the kernel entropy pool is not initialized, the syscall is unavailable or blocked, rather than falling back to potentially uninitialized early-boot `/dev/urandom`. The API requires an appropriate Linux kernel/libc and seccomp policy; existing fallback files can still be read. An entropy failure during creation leaves a locked empty file that can be retried later; no ephemeral or fabricated ID is produced. Windows uses `BCryptGenRandom` with `BCRYPT_USE_SYSTEM_PREFERRED_RNG` (`<bcrypt.h>`, `bcrypt` library). macOS uses `SecRandomCopyBytes` (`<Security/SecRandom.h>`, Security framework). These two adapters are experimental and not yet connected to Windows/macOS persistence. The values are not logged. Test success does not measure entropy quality, validate every distribution or grant a security certification.

## Sources and uncertainty

Accessed 2026-11-22. Linux [`clock_gettime`](https://man7.org/linux/man-pages/man2/clock_gettime.2.html) says `CLOCK_MONOTONIC` excludes suspend. Apple's [clock guidance](https://developer.apple.com/forums/thread/130083) links `CLOCK_UPTIME_RAW` to a sleep-excluding clock, and Apple's [`mach_absolute_time`](https://developer.apple.com/documentation/kernel/1462446-mach_absolute_time) documentation describes an equivalent intended distinction. Microsoft's [unbiased interrupt time](https://learn.microsoft.com/en-us/windows/win32/api/realtimeapiset/nf-realtimeapiset-queryunbiasedinterrupttime) excludes sleep and hibernation; its [QPC guidance](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps) describes QPC and its different sleep behavior. Microsoft documents [SRW lock initialization and lifetime](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-initializesrwlock), as well as [BCryptGenRandom](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptgenrandom). Linux [getrandom](https://man7.org/linux/man-pages/man2/getrandom.2.html) documents initialization, failure and short reads; Apple discusses [SecRandomCopyBytes](https://developer.apple.com/forums/thread/694129).

These sources specify APIs, not physical-device accuracy, identity, permissions for collection or sleep behavior in every VM. Test runner results do not substitute for actual suspend/resume testing. No device data is collected by the primitive conformance test. No elevated permissions are intended; CI identity, OS version/architecture and actual runner results must be recorded before making any support claim. Windows 11 x64 and both macOS architectures remain release goals, not accepted support claims.

## Tests and remaining work

`tests/test_platform.c` checks entropy call status and argument bounds without printing bytes, nondecreasing readings, null/error handling, mutex-protected concurrent admission, saturation and reset. `tests/test_store_faults.c` uses a synthetic adapter to inject initialization, lock, unlock, clock and entropy failures, backward time and fractional refill; it tests public C decisions and no accidental allow. `tests/platform/CMakeLists.txt` builds only these primitives, not installable Archx artifacts. Native CI for Windows Server 2022 x64, macOS 15 arm64 and macOS 15 Intel exercises this subset; actual results and architecture must be checked in the run, not inferred from the configuration. Sleep/resume, Windows 11, complete native core builds, hardware signals, permissions, fallback, ABI/export/loading and release artifacts are not yet tested or implemented.

At commit `05456c4`, [native primitive run 45664521871](https://github.com/archnemix/Archx-RL/actions/runs/45664521871) passed Windows Server 2022 x64 and macOS 15 Intel; macOS arm64 was still queued when checked. Those results predate the entropy changes and therefore do not validate the entropy adapters. No Windows 11 or macOS sleep/resume evidence exists.

At commit `4780092`, [native primitive run 45665565153](https://github.com/archnemix/Archx-RL/actions/runs/45665565153) passed the entropy, clock, mutex and store subset on Windows Server 2022 x64, macOS 15 Intel and macOS 15 arm64. The [Linux full regression](https://github.com/archnemix/Archx-RL/actions/runs/45665565162) also passed. This is not evidence for complete native builds, collectors, fallback storage, bindings or sleep/resume.

At commit `ab3231a`, [native synthetic run 45808839990](https://github.com/archnemix/Archx-RL/actions/runs/45808839990) passed the collector-independent canonicalization fixture together with the existing primitive tests on Windows Server 2022 x64 and macOS 15 arm64/Intel. [Linux regression 45808839955](https://github.com/archnemix/Archx-RL/actions/runs/45808839955) passed GCC/Clang CMake installation and the full Linux suite. This demonstrates only a synthetic canonicalization boundary, not complete platform support, real signal collection, fallback or Windows 11.

## Internal thread-local declaration

The C core error buffer now uses an internal macro selecting C11 `_Thread_local` or MSVC `__declspec(thread)`. A synthetic platform fixture synchronizes eight native threads before verifying isolated slots; Linux core tests additionally create different simultaneous `ax_last_error` values. [Microsoft documentation](https://learn.microsoft.com/en-us/cpp/c-language/thread-local-storage?view=msvc-170) notes potential delay-load interactions. These tests do not execute the full Windows/macOS core or prove TLS works in a native shared library loaded into pre-existing threads; that remains open under C02.
