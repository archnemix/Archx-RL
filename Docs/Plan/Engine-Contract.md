# Python engine behavior contract (prototype)

Scope: `demo.engine.Engine` (one process, memory) and `demo.sqlite_engine.SQLiteEngine` (one host, SQLite file). This is a description of their current behavior, not a production-support, distributed-consistency, rollback-resistance, or authentication claim. The two engines use the same policy, secret, clock and `max_entries` in the shared tests. A caller must not mix workers using independent memory engines and assume a global quota.

## Shared behavior

- `prepare` validates and normalizes selected signal inputs and a transport-provided peer address, creates keyed signal tokens, and checks timezone/timestamp policy. The legacy `account` input is ignored for identity. Invalid input can raise before a direct engine check charges anything; `RequestService` first precharges the peer, and handles validation failures separately.
- Direct `check` samples the state clock inside the memory mutex or SQLite writer transaction, removes up to 64 expired fixed windows and denies without charging if more remain. Once the window backlog is clear it removes up to 64 expired observations and then checks whether **all** needed new keys fit. If not, it denies `capacity_exceeded`, with the configured window as retry, without charging existing or new keys. Otherwise it charges every selected signal and peer key, including when the resulting quota or policy check denies. The quota boundary is strictly `count > max_requests`; rate-limit retry is the greatest remaining applicable window rounded up. Windows expire when `start <= now - window_seconds`.
- Missing-required or timezone/clock enforcement decisions occur after direct-check charging and are not enrolled. The `RequestService` separately precharges the peer before parsing, decryption and external checks; it rejects certain policy/provider failures **before** device-key charging. Successful service calls use internal `_ip_precharged=True` to avoid charging the peer twice. This two-stage process is not an atomic reservation over slow work, and the precharged window can expire before the second stage.
- Matching counts name/token pairs within one previous observation only; it never combines different observations to meet a threshold. A duplicate snapshot refreshes its history expiry without adding a slot. At history capacity, distinct snapshots are denied rather than evicting live history; an identical snapshot may refresh. When full, retry is the rounded-up interval to the earliest expiry, at least one second. An expiry at or before the current state time cannot be matched.
- `reject_malformed` precharges only the peer. It returns `None` when charged but not limited, otherwise a rate/capacity decision with the same window retry behavior. A caller that invokes direct `check` after it without `_ip_precharged=True` will charge that peer again. This internal flag is not an authorization boundary and should not be exposed to an untrusted caller.

## Explicit differences and limitations

- Both memory and SQLite remove at most 64 expired windows per valid or malformed request. If any expired window remains, they deny `capacity_exceeded` with one-second retry before charging any key. Once windows are clear, a valid check removes at most 64 expired observations; if more remain and the request otherwise reaches matching, it denies after applicable quota charges without matching or enrollment. Matching resumes only after the backlog is clear. Malformed requests do not prune history. SQLite commits the cleanup before returning these decisions. Neither backend offers idle cleanup; backlogs can deny legitimate requests until drained.
- Memory stores exact token tuples for duplicate lookup; SQLite uses a SHA-256 fingerprint of a canonical token tuple. The latter assumes collision resistance. Both only retain raw IPs if explicitly configured to do so; keyed tokens remain linkable pseudonymous data.
- Memory state is process-local and lost on restart. SQLite transactions persist a single host's state and handle a detected SQLite error by rolling back and returning `storage_error`; this does not prevent deletion, rollback to an older backup, runtime tampering, crash/ambiguous-commit errors, or arbitrary non-SQLite exceptions. A database writer may wait up to its configured busy timeout; that is not an end-to-end deadline. SQLite startup validates its expected schema and metadata, not the authenticity or completeness of all data.
- Wall-clock jumps or restored state can reset/extend windows or change history behavior. No reset-proof or cross-host guarantee is made. The per-request cleanup budget does not bound all other work: popular tokens can have capacity-sized postings, and SQLite transaction, I/O, indexing and lock waits have no wall-clock bound.

## Evidence

`tests/test_sqlite_engine.py` runs a seeded shared synthetic scenario, duplicate-refresh/expiry parity, new-key saturation and no-charge recovery, malformed peer precharge, and bounded window/history backlog parity. `tests/test_expiry_cleanup.py` covers the window heap against a reference model, exact expiry, no charge while stale windows remain, concurrency and recovery. `tests/test_observation_index.py` compares the bounded memory index against a linear oracle and tests independent-observation matching, concurrency, capacity and expiry. The tests describe selected scenarios and do not prove parity for every input, storage fault, timing, deployment, or malicious client. See the [release backlog](Next-Version.md) for remaining storage, overload, fault and production work.
