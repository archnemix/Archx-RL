## D07 C-store collision bound and cost

Admission now finds an existing bucket or inserts in one traversal rather than scanning twice for a missing key. Full-table admission never evicts an existing bucket. A single lookup/admission probes at most the rounded table capacity; reset can inspect at most capacity slots to find the key and up to capacity minus one more to shift the cluster. Public configuration accepts 16 to 1,048,576 entries, rounded up to a power of two. Mutex wait, scheduling, and elapsed wall-clock time have no fixed bound; worst-case scans are not a latency guarantee. The internal constructor also rejects power-of-two/allocation-size overflow.

The synthetic single-thread [collision benchmark](../Test-Results/unreleased/store-collision-benchmark.json) was compiled with GCC 12.2.0 `-O2` on Linux x86-64. At 8,192 completely colliding slots, full missing-key p50/p95/p99/max were 11.893/21.742/31.185/72.975 microseconds; reset-and-shift p50/p95/p99/max were 14.560/14.645/27.655/28.226 microseconds. Setup is excluded; operations include clock and lock costs, timings are host-specific and **not** a production capacity target, measurement of the maximum configured capacity, concurrent contention, or an upper wall-time bound. HMAC-generated real keys do not intentionally share this artificial home slot. `tests/test_platform.c` verifies the worst-case chain, full saturation, deletion shifting and preserved quotas; the same fixture is built by native primitive CI. Reproduce using the compile command in `tools/store_collision_benchmark.c`.

## D04 serialization profiling and future sharding semantics

`tools/contention_benchmark.py` instruments the memory mutex and the SQLite `BEGIN IMMEDIATE`/commit writer boundary without changing the engines. Synthetic, closed-loop eight-thread hot-key runs used 800 direct checks, quota 100 and a fixed clock; each admitted exactly 100 and rate-limited 700. The memory [measurement](../Test-Results/unreleased/contention-memory.json) reports mutex wait p50/p95/p99 0/0/0.001 ms and held 0.002/0.007/0.016 ms. SQLite [measurement](../Test-Results/unreleased/contention-sqlite.json) reports writer wait 0.017/0.105/56.275 ms and held 0.794/1.215/1.477 ms; maximum wait was 734.011 ms. [Memory](../Test-Results/unreleased/contention-memory-single.json) and [SQLite](../Test-Results/unreleased/contention-sqlite-single.json) single-thread reference runs use 500 checks, so counts and runtime are not identical. Python 3.11.2, Linux x86-64; measurements include instrumentation overhead and SQLite connection work is outside writer-boundary timing. They are not an open-loop, network, multi-process, soak or production capacity assessment; rounding can show sub-microsecond memory waits as zero.

Before any sharding, a design must preserve atomic capacity checking and all-key charging, a single consistent state timestamp, no quota oversubscription under races, per-observation matching (never aggregate devices), duplicate refresh and cleanup semantics, and fail-closed behavior on partial failures. It must explicitly define lock ordering, rollback on a failed multi-shard update, shared-IP/multi-signal interactions and serialization with reset/expiry. The existing C store remains one mutex; SQLite remains a single writer and its busy timeout is not an overall deadline. No sharding or general end-to-end contention reduction is claimed. `tests/test_contention_benchmark.py` checks timing accounting and concurrent quota invariants in both modes without performance thresholds; this limited evidence does not replace multiprocess or production race testing.

The pre-index and indexed matching loops were also [compared](../Test-Results/unreleased/index-match-comparison.json) on 5,000 synthetic snapshots with exactly one matching observation, 100 samples, and result parity each time. On the same Linux/Python runner, linear matching p50/p95/p99 was 2.262/3.208/3.364 ms and indexed matching 0.009/0.013/0.016 ms. This narrowly demonstrates reduced matching work inside the memory lock for this sparse case, **not** a full critical-section or concurrent before/after comparison. The historical loop did not have the same enrollment and eviction semantics; the measurement excludes those operations. Common-token postings, window scanning, SQLite transactions, multi-process races and capacity-scale performance remain unbounded by this sample.

## D03 bounded window and SQLite cleanup follow-up

Both engines now remove at most 64 expired windows per request, using a no-tombstone indexed heap in memory and indexed bounded deletes in SQLite. If a backlog remains, requests fail closed with retry 1 **before charging**. A valid check then removes at most 64 expired observations in either backend; if that backlog remains, it fails closed before matching or enrollment but after applicable charges. Malformed precharges clean windows only. This changes the old SQLite transaction-wide cleanup behavior and removes the prior in-memory full-window rebuild. The clock comparison now uses the SQLite cutoff expression in both engines. Expired windows are never charged and expired observations are never matched, even amid a backlog.

`tests/test_expiry_cleanup.py` checks a seeded linear window oracle, heap invariants, exact boundaries, no charges on an incomplete window backlog and concurrent recovery in both backends. `tests/test_sqlite_engine.py` tests shared window/history backlog parity. In synthetic sequential 5,000-window/5,000-observation backlog measurements, [memory](../Test-Results/unreleased/cleanup-indexed-memory.json) and [SQLite](../Test-Results/unreleased/cleanup-indexed-sqlite.json) each removed at most 64 per category per check, denied 156 checks while draining and recovered with a `new` relation on check 157. Memory p50/p95/p99/max were 0.442/0.711/0.768/0.829 ms; SQLite 1.324/2.261/4.491/4.953 ms. Linux x86-64/Python 3.11.2, synthetic, setup excluded and stale-count queries can warm caches. These are not capacity targets, full end-to-end performance or wall-clock bounds. No idle cleanup runs; scans of popular token postings, SQLite I/O, and lock waits can still take unbounded wall time.

## B05 builder, allocation and fallback persistence follow-up

C output/digest formatting now checks formatting errors before hashing or publishing; `ax_check` denies and `ax_reset` reports internal failure if bucket-key formatting fails. Profile comparison reports internal error rather than treating a formatting failure as an invalid profile. The fallback Linux ID is exposed only after successful unlock and close, and invalid NULL output is rejected. A failure after a write/unlock does **not** imply a durable rollback; partial files remain fail-closed, requiring explicit operator recovery. This does not establish crash durability or no-silent-reset.

`tests/test_output_faults.c` injects each formatting call across collect, identify including fallback, profile, comparison, check and reset, verifies no partial output or unintended allow, and recovers. `tests/test_core_alloc_faults.c` fails each core/store calloc and checks cleanup; parser and output malloc faults are exercised separately. `tests/test_store_faults.c` covers mutex initialization/lock/unlock, time, entropy and denial, including the ambiguity that unlock failure can follow a completed charge/reset. `tests/test_fallback_faults.c` injects mkdir/open/flock/fstat/read/write/fsync/unlock/close failures and partial-file recovery using synthetic temporary data. These are targeted synthetic faults, not a proof of every OS/filesystem failure or of crash durability.

## B03/B11 WSGI boundary prototype (partial)

`examples/python/boundary_wsgi.py` adds a process-local global request token bucket and a non-queuing in-flight cap around the entire WSGI app, including GET, challenge, invalid and protected routes. It holds a permit through lazy response iteration, denies clock failure and overload, supports stopping new admission and timed drain waiting, and releases permits on application, iterator and close errors. `is_ready` is an instantaneous local admission signal, not a full dependency or deployment health check. `tests/test_wsgi_boundary.py` covers synthetic rate, concurrency, failures, recovery, draining and a host-wrapped route.

This is not a supported server: TCP accept/worker/kernel queues, slow clients, request header/body bounds and upstream deadlines must be imposed by a separately verified server/proxy. Limits are per process; no cluster-wide quota, cancellation of stuck application work, TLS or authentication is supplied. Therefore #19, #27 and #29 remain open; this experiment is not production-readiness evidence.

## B08 separate thresholds and synthetic shared-IP simulation (partial)

Optional `ip_max_requests` and `device_max_requests` apply distinct thresholds in both Python engines, with `max_requests` retaining its previous default role when omitted. Both use one `window_seconds`; malformed/service precharge uses the IP threshold, while direct and service device checks use the device threshold. A duplicate internal bucket key is charged once at the stricter threshold. Explicitly changing thresholds changes the persisted SQLite policy fingerprint, so an existing database rejects mismatched settings rather than silently resetting enforcement; there is no migration mechanism yet. `tests/test_separate_quotas.py` checks invalid policy, direct/service behavior, backend parity and restart behavior.

The [synthetic simulation](../Test-Results/unreleased/separate-quota-nat-simulation.json) assumes 30 distinct submitted values behind one documentation IP are legitimate: with device quota 1 and IP limits 5, 15 and 30, respectively 25, 15 and 0 requests were rate-limited in both engines. These are illustrative request counts, **not** measured people or a real-world false-positive rate. Increasing IP allowance also enables more abuse; shared IP is not identity, and forged/rotating signals and poisoning remain. Progressive challenges and authenticated host-controlled recovery remain unimplemented, so #24 remains open.

## A10 fixed-cardinality metrics follow-up

## D06 short mixed-process SQLite probe (partial)

A [local synthetic probe](../Test-Results/unreleased/sqlite-multiprocess-probe.json) starts four writer processes (100 checks each), two reader processes (100 read-only aggregate queries each), and two processes racing one replay nonce against one temporary WAL database. On this Linux x86-64 runner, all 200 reads completed; writers produced exactly 100 allows and 300 rate-limit decisions, both window counts were 400, and one replay consumed the nonce while the other was rejected. Total wall time was 0.86 s including process startup; this is not a performance target or a sustained soak. Reader work completed early, so continuous read/write overlap is not guaranteed. `tests/test_sqlite_multiprocess_probe.py` runs a smaller invariant smoke in CI. Existing busy-writer, missing-schema and rollback fault injections remain in `tests/test_sqlite_engine.py`; existing replay tests cover persistent single-use and schema failure.

These synthetic cases do not establish invariants under arbitrary process death, disk-full, fsync failure, network filesystems, power failure, prolonged mixed contention or all WAL/checkpoint behaviors. They also do not measure connection churn costs or a production workload. #39 remains open pending sustained contention/fault evaluation and full profiling.

## B07 source-specific signal normalization

[Signal-normalization notes](../Research/Signal-Normalization.md) describe conservative Linux C, experimental Windows SMBIOS/macOS UUID and Python raw-v2 rules, known differences and evidence. The Linux C collector now rejects incomplete/embedded-NUL reads, I/O and close failures, malformed/placeholder machine IDs and UUIDs, invalid/non-ASCII/placeholder board strings, and excessive lengths. This can make formerly accepted inputs unreadable and change derived identifiers; there is no migration. Synthetic fixture tests cover short and interrupted reads, I/O faults, truncation, vendor placeholders, absence and malformed/Unicode data. No syntax check proves source authenticity, a stable person/device, real-vendor coverage, platform support or privacy authorization.

## A13 experimental idle expiry (partial)

## B08 progressive shared-IP challenge and privileged recovery

Optional `ip_challenge_after` adds a denial requiring host follow-up before the hard peer quota; hard limits win. `reset_ip_window` resets one peer bucket without resetting device limits, observations or replay. ## A13 explicitly configured retention plan

The optional [retention plan](../Guides/Retention.md), supervised by the idle worker, adds bounded expired replay cleanup, an explicitly authorized drop of one recognized retired trial schema, narrowly scoped age-based deletion of named files in an operator-owned private backup directory, and passive WAL checkpointing.
