# Project working rules

Purpose: practical rules for changes to the existing Archx repository.

- Read these rules at the start of each implementation change. Keep names, responsibilities, structure and code readable; prefer focused modules and concise purpose comments when the file format supports them. Avoid unrelated rewrites or unnecessary files.
- Preserve the current C/Python/JavaScript technology and accurately document current Linux-only native support; do not switch languages or claim unsupported platforms without a request and implementation.
- Work from the actual code and user requirements. Research relevant external APIs and libraries before using or changing them; record useful sources in `Research.json`. Ask when a consequential requirement is genuinely ambiguous, and test claims rather than guessing.
- Finish and test the current change before adding unrelated work. Keep unit tests focused on meaningful behavior and run integration tests for changed interfaces. Regression tests may be rerun even when their own source is unchanged, because dependencies can change.
- Test supported platforms where practical. Linux is the only implemented native platform today. Windows and macOS are required for the next version, but must not be claimed supported until native implementation and execution evidence exist; add native CI rather than report Linux checks as portable.
- Keep useful, sanitized test records under `Docs/Test-Results/`, organized by release or `unreleased`, and retain at most the current and previous two release groups. Do not save real identifiers, secrets, request bodies or bulky generated output. Never fabricate historical logs or version numbers.
- Use the existing repository-backed GitHub runner when local capabilities are insufficient. Run no more than five runners concurrently; avoid unnecessary jobs, and keep outputs sanitized. Never store credentials in the repository, even in `Secrets.md` or logs.
- Maintain the relevant architecture, roadmap, change notes, file index, research and decision summaries as the project changes. `Thinking.md` records concise decisions, problems and outcomes, not private chain-of-thought. `Changelog.md` distinguishes unreleased changes from actual versions; avoid inventing releases.
- Keep documentation proportionate: directory READMEs describe maintained source folders, not generated caches, Git internals or historical runner outputs. JSON and other strict formats cannot contain comments; use adjacent docs or the file index instead. Do not mechanically rewrite untouched files solely for a header.
- Archx identifies related requests probabilistically and rate-limits; it is not authentication, an account system or trial enforcement. Never imply stronger identity, security, privacy or platform guarantees than demonstrated by the code and tests.
