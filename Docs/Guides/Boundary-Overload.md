# Single-process overload controls

The private demo applies one coarse **connection** token bucket and one concurrency limit before dispatching any handler, including the actual home page, challenge endpoint, demo simulation and check endpoint. Defaults are 25 new connections per second, burst 50, at most 32 active handlers, an OS listen backlog request of 64 and an absolute 15-second socket lifetime. Options are bounded and configurable through `demo/server.py --help`. An available token is spent before the concurrency check, even when the handler pool is full. On overload the server closes the accepted connection without attempting a potentially blocking error response. The demo processes only one request per connection, including pipelined HTTP, so that bucket also limits admitted requests. A connection's socket is shut down after its absolute deadline even if the client dribbles data. Slots are released when the corresponding handler exits, not simply when its socket is shut down.

`tests/test_boundaries.py` sends real GET, enabled challenge, simulation POST and check POST paths through the same admission bucket; it also saturates two slots with incomplete bodies and probes mixed real routes concurrently, tests an incomplete-header dribble, verifies a pipelined request cannot bypass the bucket, and checks recovery after disconnect or deadline. A stalled handler remains counted and denies other connections until it returns. In the separate [experimental nginx/Unix candidate](../Research/Ingress-Candidate.md), nginx applies shared request-rate and active-request zones to all proxied paths and methods; its integration tests verify TLS, mixed-route admission, slow bodies and recovery. Its local socket, timeout and trust limitations are documented there.

**These are single-process/one-worker controls, not a production deployment guarantee.** An application callback or dependency that stalls indefinitely can permanently hold a handler and cause denial of service; Python cannot forcibly cancel it. TCP backlog, nginx, Waitress, kernel resources and independent instances are separate limits; these tests do not establish fairness, capacity under sustained attacks, host resource budgets or multi-host coordination. Socket deadlines do not cancel application work. The private demo must not be exposed directly; there is currently no supported production deployment profile. The separate supported-entrypoint and proxy-trust work remains open, as do operational monitoring, identity, persistence, rotation and recovery. See [deployment status](Deployment.md).
