# Experimental WSGI health and draining

`examples/python/boundary_wsgi.py` can wrap the whole host application with a finite process-local in-flight cap, token-bucket request admission and no application-side waiting queue. Requests over the cap or rate limit are rejected with a generic 503; this includes health checks. The wrapper is disabled unless the host explicitly constructs it, and its limits do not coordinate across processes. It is **not an HTTP server**: accepted sockets, server/kernel/upstream queues, TLS, request sizes and deadlines still need independent controls. The private demo's separate `BoundedDemoServer` has a finite listening backlog and admitted-handler cap, but it is not a supported production deployment.

Optional `readiness_probe` must be callable and return exactly `True` during construction, otherwise startup fails. On each admitted application request, a false, non-boolean or raised probe result returns 503 without invoking the protected application. The host controls what the probe verifies; the wrapper does not automatically validate a database, credentials, remote provider or transport. Probe errors are not exposed to clients. A probe executes under an admission permit but is not time-limited or cancelled; the host must use independently bounded probes. Calling `is_ready()` runs the probe outside a request permit and can also block. Readiness is instantaneous and can change immediately after it is sampled.

If `health_routes=True`, `GET /health/live` returns 200 while the wrapper can admit the health call, independently of the readiness probe; `GET /health/ready` checks local spare admission capacity and the optional host probe. Both consume the same global admission budget, return no sensitive details and may return 503 due to saturation, rate limiting, a failed clock or draining. Liveness does not prove that dependencies are healthy. Routes are disabled by default to avoid shadowing a host application's endpoints. Restrict and monitor health endpoints appropriately in a real deployment.

`stop_accepting()` permanently denies calls arriving after the drain transition. Work admitted before that point may still complete and execute; the wrapper cannot cancel it. Its permit remains held through lazy response iteration until exhaustion or close. `wait_drained(timeout)` returns `False` if admitted work is still active, and does not terminate threads or shut down the underlying server. Hosts must stop accepting network connections, honor drain timeouts, supervise processes and independently bound stalled code. No general production shutdown or upstream queue guarantee is made.

`tests/test_wsgi_boundary.py` covers startup validation, a failing/recovering dependency, non-boolean and exception failures, overload, process-local admission, lazy-response permit release, shutdown races, and a real loopback HTTP integration where denied calls never invoke the synthetic protected operation. It does not establish real TLS/proxy, distributed readiness, production availability, or a cancellable deadline.
