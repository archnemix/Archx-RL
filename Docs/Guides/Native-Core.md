# Native C core (Linux prototype)

The C ABI in [`include/archx.h`](../../include/archx.h) is currently implemented for Linux. The C core reads Linux installation/firmware signals, constructs an app-scoped HMAC pseudonym and manages a mutex-protected **in-process** token-bucket store. Experimental [Python and Node bindings](../../bindings/README.md) call that ABI and require a trusted explicit library path. It is separate from the Python request-policy engine; their quotas, APIs and persistence are not interchangeable. Experimental Windows/macOS primitive and fixture runs are not full native core or collector support.

Numeric IP normalization and the collection/fallback calls are routed through internal platform interfaces rather than POSIX headers or Linux collector names in the common core. Synthetic platform tests cover IPv4, IPv6 and invalid or insufficient-buffer cases; they do not establish identical formatting for every valid address on every OS or cross-platform profile compatibility. Native fixture CI also builds and loads the real ABI using a **synthetic Linux-shaped collector** to exercise profiles, decisions, buffers and collection failure without reading host identifiers. This is not a Windows/macOS product collector: ABI-v1 capability metadata and profile scope remain Linux-specific, and secure native fallback persistence, full native collection and distribution are not implemented. The portability issues remain open.

For build, installation, API and profile examples see the [root README](../../README.md#build-and-try). `ax_collect` reports metadata, not raw IDs; the optional [versioned capability schema](Capability-Schema.md) distinguishes collection outcomes and browser limitations. `ax_identify` returns a pseudonym. ABI-v1 `confidence` is an availability heuristic, not an accuracy probability, and fallback's value 10 is a historical marker. Signals are forgeable and profile matching is not authentication. Keep peppers secret, protect stored profiles, and use `ax_buffer_free` for returned buffers.

New bucket keys fail closed when the store fills; no live bucket is silently evicted. Explicit reset affects a bucket and process/handle destruction resets all quotas. The store is neither durable nor distributed. See [threat model](../Threat-Model.md) and [next-version backlog](../Plan/Next-Version.md) before considering any deployment.
