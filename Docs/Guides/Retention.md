# Experimental single-host retention controls

**Destructive operations require explicit operator configuration and review.** Neither the demo nor the library automatically starts this plan. The operator must establish legal retention, authentication, authorization, backup and recovery procedures before use. These controls provide logical cleanup only, not secure deletion, tamper resistance or a supported production retention service.

`RetentionPlan` in `demo/retention.py` composes optional operations for the opt-in `IdleCleanup` worker described in [Idle Cleanup](Idle-Cleanup.md). Each operation runs separately; the whole plan is **not atomic**. An earlier deletion can succeed before a later step fails, and a post-commit close failure can report an error after a change. The host must inspect and externally monitor worker `status()`, and shutdown does not cancel blocked I/O. Do not run old and new software concurrently when retiring legacy data.

- **Expired state:** engine batches remove at most 64 expired windows and 64 observations; an explicitly supplied memory/SQLite replay store removes at most 64 expired challenges. Expiration runs even without requests. Memory replay may scan its capacity, and SQLite I/O/locks have no overall time bound. No live quota, observation or challenge is intentionally removed. Wall-clock changes and old restores affect expiry.
- **Retired trial data:** `purge_retired_trial=True` **drops both entire legacy trial tables and their marker**, not merely expired records. It is only for operators who have definitively retired that old feature and independently decided retention and backup needs. The plan recognizes one exact historical table schema and rejects incomplete/unknown variants; it does not delete unrelated tables. Dropping can destroy active entitlements from older deployments. Leave the default `False` unless explicitly authorized.
- **Backup files:** provide an absolute, separate, private owner-only backup directory and `backup_min_age_seconds` of at least 86,400. Only regular, owner-owned, private, single-link files matching `archx-backup-YYYYMMDDTHHMMSSZ.sqlite`, older by filesystem modification time, with no `-wal`, `-shm` or `-journal` sidecar, are eligible. Up to 64 files are unlinked per pass; directory listing/sorting itself is not bounded. The directory and its parent must be trusted and not concurrently writable or subject to symlink/race manipulation. There is no protection against falsely old timestamps, held-open files, file replacement races, required recovery points, copies elsewhere or backups under other names. **Never point the plan at the active database directory.** It rejects the current database's parent, including resolved aliases. Backups are not created or verified by this feature. The operator must choose minimum retention, ensure the recovery set is adequate, and protect unrecognized files and sidecars separately.
- **WAL:** `checkpoint_wal=True` requests SQLite `wal_checkpoint(PASSIVE)` and records busy/log/checkpointed frame counts. Long readers can prevent progress; `busy=0` does not imply all frames were checkpointed. It does not force readers out, truncate the WAL, or erase old bytes, snapshots or backups. WAL file lifetime and storage behavior are outside this plan.

A minimal illustrative setup is `IdleCleanup(RetentionPlan(engine, replay=replay, checkpoint_wal=True), 60)`, followed by `start()` and supervised `stop(timeout)`. This example does **not** enable legacy or backup deletion. Do not schedule destructive options until the operator has supplied and reviewed the explicit settings and established an independent audit and recovery plan.

`tests/test_retention.py` uses temporary synthetic data to exercise bounded idle replay expiry, exact-cutoff and live-challenge behavior, safe backup selection, held-open file behavior after unlink, legacy schema rejection and transaction rollback, and a pinned WAL reader with a passive checkpoint. A removed pathname can remain readable through an open descriptor, and deleted bytes can persist in WAL, SQLite free pages, snapshots, filesystem journals, cloud replicas or hardware. Neither `secure_delete`, unlink, checkpoint, nor these tests guarantees physical erasure. Clock behavior, arbitrary corruption, file races, filesystem snapshots, backup restoration, crashes and operational recovery need separate testing and controls.
