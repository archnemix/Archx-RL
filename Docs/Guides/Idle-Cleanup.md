# Experimental idle cleanup

Memory and SQLite engines expose `cleanup_expired()`, which removes **at most 64 expired windows and 64 expired observations per call**, including when no request arrives. Returned booleans indicate whether expired entries remain; live entries are not reset. SQLite performs the two batches in a writer transaction and propagates errors. A failure at or after commit does not guarantee rollback. The memory path holds the same lock used by requests, but a mid-batch exception does not imply transactional rollback. Both use the engine's wall clock; clock jumps can expire data early or late. SQLite's five-second busy timeout does not bound all filesystem or transaction delays.

The optional `demo/maintenance.py` `IdleCleanup(engine, interval_seconds)` runs one batch immediately and then periodically (0.1–86400 seconds); it is **not started automatically** by the demo. The host must choose the interval, start it once, inspect `status()` and stop it with a finite timeout. `last_failed` indicates the latest batch failed without retaining exception text; a subsequent successful batch clears it. `pending` reports only the last successful snapshot and can become stale. A false return from `stop(timeout)` means the worker is still running, not that its operation was cancelled. Failures must be monitored externally, and the daemon thread may be lost on abrupt process shutdown. Multiple workers can safely serialize but increase contention; a single-host operator must choose and supervise the worker.

This removes logical rows, **not** old bytes from WAL, backups, legacy tables, filesystem snapshots or underlying media. It does not remove replay challenges, rotate keys, handle backup retention, or guarantee secure physical deletion. SQLite `secure_delete`, checkpointing, storage encryption and deletion behavior have their own limits. No general-purpose backup or legacy-table deletion is automated because arbitrary destructive deletion would risk state and recovery. Configure independent retention and recovery processes before using real data. Test evidence in `tests/test_idle_cleanup.py` covers idle expiry boundaries, 64-item batches, preserved live data, concurrent calls, a synthetic SQLite rollback, worker failure/retry and stalled shutdown. This is a prototype, not a supported service or production retention solution.
