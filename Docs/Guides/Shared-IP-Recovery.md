# Experimental shared-IP thresholds and recovery

The Python prototype accepts optional independent `ip_max_requests` and `device_max_requests`, both defaulting to `max_requests` and sharing `window_seconds`. Optional `ip_challenge_after` must be a positive integer strictly below the effective IP maximum. The first `ip_challenge_after` peer charges proceed normally, further charges up to the IP maximum return `challenge` with reason `rate_challenge`, and later charges return `rate_limited`. This is a **denial requiring host follow-up**, not an implemented verification provider or automatic bypass. The soft threshold is disabled by default. It applies to malformed peer precharges too; precharge can challenge before a sealed body is decrypted or its nonce consumed. In direct engine calls all keys are charged and their hard-limit denials take precedence over the soft challenge; in `RequestService`, only the peer is charged before a soft challenge, so device limits are not checked on that attempt. The peer hard limit takes precedence over its soft threshold. A host must not execute protected operations on a challenge or treat it as proof of abuse or identity.

`reset_ip_window(peer)` is an explicitly privileged, single-bucket operator operation in both prototype engines. It canonicalizes IPv4-mapped IPv6 and serializes with requests; it removes **only** that IP's window, not device buckets, observations, replay state or other IPs. It affects every client sharing that IP, can restore an attacker's allowance, and does not establish which person owns or uses an address. Do not expose it to clients without independently authenticated, authorized, reviewed and audited host controls. A storage/close failure after commit may report an error even if the reset occurred; this is not an all-or-nothing proof across system crashes. Clock rollback, database restoration and malicious signals remain separate risks.

The local-only WSGI example exposes `/recovery` **only if** the host explicitly supplies principal resolution, operation authorization, separate recovery approval, and an audit hook. Each must approve exactly `True`, and audit is called **before** reset as an attempt record; a later reset may fail or have an ambiguous result. The example never grants a protected action as part of recovery. It uses only `REMOTE_ADDR`, never a client forwarding header; a host must establish that transport boundary itself. This illustrative route does not implement a real identity system, durable audit, CSRF defense, per-principal recovery rate limits, operator workflow, TLS, or a production server. All are host responsibilities. Enabling it without those controls would allow abuse or denial of service, particularly on NAT networks. The default example leaves recovery disabled.

The [synthetic shared-NAT simulation](../Test-Results/unreleased/progressive-nat-simulation.json) assumes 30 distinct legitimate requests behind one documentation IP, threshold 3 and IP maximum 5. Without resets, both engines return 3 allows, 2 challenges and 25 rate limits. If a trusted operator is assumed to reset the shared IP window after each group of five, the same model returns 18 allows and 12 challenges after five resets. These are illustrative request counts, not a real false-positive rate, measured people, demonstrated identity, or evidence that such frequent reset is safe. For comparison, [separate-quota simulation](../Test-Results/unreleased/separate-quota-nat-simulation.json) shows how raising the IP threshold changes modeled collateral impact. Signals can be forged or rotated; resetting a shared bucket can also benefit attackers.

`tests/test_progressive_recovery.py` checks both engines, default-disabled thresholds, challenge/hard-limit ordering, peer precharge, targeted reset, persistent-policy mismatch, synthetic storage failures, host authorization/approval/audit failures, and model counts. Changing thresholds in persistent mode changes the policy fingerprint and requires an explicit migration or new store; no migration is supplied. This prototype is not a supported production recovery service.
