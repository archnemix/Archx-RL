# ADR dossier: Windows and macOS signal and fallback decisions

**Date of decision and source review: 2026-11-22.** Scope: the research/decision deliverable in #42. These decisions are deliberately conservative: they do **not** approve Windows or macOS releases, resolve Apple's terms, or implement native fallback. Each entry distinguishes an implemented experiment from a proposed API and records missing evidence. Product implementation and support remain in #4, #5, #6, #7 and #30; privacy/distribution approval is a separate release gate. Nothing here makes a device signal authentication, proof of a person, a hardware attestation or a guarantee of uniqueness.

## Decision matrix and applicability

| ADR | Decision | Current implementation and distribution |
| --- | --- | --- |
| W1 | Use bounded Windows RSMB only for the internal collector experiment. | `src/signals_windows.c`/`src/smbios.c`; Windows Server 2022 x64 hosted tests. No Windows product artifact or UWP/Store support. |
| W2 | Do not collect MachineGuid for the product; retain metadata-only permission survey as research. | `tools/permission_survey/native_windows.c` checks registry value type without reading the value; no product collector. |
| W3 | Defer Windows per-user fallback implementation until the required filesystem/security design and tests pass. | No Windows fallback exists. The API selection below is a candidate design, not a security guarantee. |
| M1 | Do not enable an IOKit device-identifier collector for distribution pending purpose-specific policy review. | The native survey checks property *types* only; `src/macos_cf_uuid.c` validates caller-supplied CF values, not registry access. No macOS product. |
| M2 | Do not ship the experimental XDG POSIX fallback as a macOS fallback. Research app-container Application Support and native storage separately. | `src/fallback_posix.c` has isolated temporary-directory tests on macOS Intel/ARM; it is not wired to a macOS product. |

## W1 — bounded RSMB collection experiment

- **API/headers and sources:** `GetSystemFirmwareTable` in `<windows.h>`/`<sysinfoapi.h>` with the `RSMB` provider. Microsoft documents the [API and RawSMBIOSData layout](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-getsystemfirmwaretable). The [DMTF SMBIOS 2.6.1](https://www.dmtf.org/sites/default/files/standards/documents/DSP0134_2.6.1.pdf) and [3.8](https://www.dmtf.org/sites/default/files/standards/documents/DSP0134_3.8.0.pdf) specifications define table structures and UUID byte ordering. These are documented interfaces, not proof of authorization for a particular application.
- **Data and privacy:** the experimental parser transiently handles firmware Type 1 UUID/system serial and a single Type 2 board-or-module serial; it clears its raw buffer. These are sensitive, potentially linkable values; raw data and values must not appear in evidence or logs. The rationale is to study availability for an explicitly configured host, not to identify a person. Consent, retention, host purpose and the legal basis are unresolved.
- **Bounds and failure:** the API size-query/read is capped at 1 MiB and a changed length, allocation failure or malformed table is rejected. The parser bounds records and string sets, refuses invalid string indices and duplicate Type 1, requires a Type 127 end marker and permits only zero padding. Multiple Type 2 records are ambiguous and do not produce a board value. For SMBIOS 2.6+ it reorders the first three UUID fields; pre-2.6 source-order behavior is only a compatibility heuristic. Denied, unsupported and read-error outcomes are distinguished as far as the API permits. There is no enforced call deadline or cancellation.
- **Ordinary-user/OS evidence:** [native survey](../Test-Results/unreleased/native-permission-survey.md) records a disposable Windows Server 2022 x64 runner: RSMB success under both an elevated token and a specifically created non-elevated Users-group account. It is one virtual runner, not Windows 11, physical-device, service-account, or UWP evidence. No other Windows OS or architecture is supported by this decision.
- **Stability and alternatives:** firmware and VM values can be absent, duplicated, cloned, spoofed or changed by servicing; no uniqueness or stability claim follows. WMI/CIM and shell-command scraping were not selected for this bounded experiment because they add operational and parsing surfaces; this is not a comparative security audit. No kernel driver or elevation is required by the proposed experiment.
- **Tests/evidence:** `tests/test_smbios.c`, `tests/test_windows_firmware.c` and `tests/fuzz_smbios.c` cover synthetic records, malformed/truncated data, UUID order, provider errors and fuzzing. [Native run 45816632804](https://github.com/archnemix/Archx-RL/actions/runs/45816632804) passed; the source-level [Windows research](Windows.md) lists earlier runs and limitations. Failure-injection does not prove every firmware implementation safe.

## W2 — MachineGuid is research-gated, not a product signal

- **API/headers and sources:** the survey uses documented Windows registry calls from `<windows.h>`/`<winreg.h>` to query value-type metadata. Microsoft's [RegQueryValueExW documentation](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regqueryvalueexw) describes the registry query; it is not a documented contract that this particular registry value is a stable device identifier. Microsoft's [Windows imaging guidance](https://learn.microsoft.com/en-us/troubleshoot/windows-server/setup-upgrade-and-drivers/windows-installations-disk-duplication) warns that cloned installations need generalization. A [Microsoft Q&A discussion](https://learn.microsoft.com/en-us/answers/questions/1489139/identifying-unique-windows-installation) reports MachineGuid can differ after reinstall and be duplicated by cloning; it is not an API guarantee.
- **Data and privacy:** the product does not collect the value. The survey reports only the result/type category, not its contents, hash, length or user identity. An installation-wide, potentially linkable value has privacy cost even if hashed. Future collection requires a separate purpose, opt-in/privacy, distribution and compatibility review.
- **OS/permissions and uncertainty:** the non-elevated and elevated Server 2022 x64 survey saw string-type metadata, not the contents or their quality. The survey does not establish other users' access or Windows 11, ARM, service-account, physical-host or Store behavior. No supported Windows product is claimed.
- **Failure/time and alternatives:** missing, denied, wrong-type or unknown outcomes must not be converted to invented values. The local registry probe has no enforced deadline. MachineGuid is rejected as a hardware root of trust; an app-owned per-user random value has a different scope and does not prove device identity.
- **Tests/evidence:** `tools/permission_survey/native_windows.c`, `tools/permission_survey/validate_native.py` and `tests/test_survey.py` exercise the sanitized output boundary; [standard-user evidence](../Test-Results/unreleased/native-permission-survey.md#windows-standard-user-follow-up) describes its precise privilege limits. There is no MachineGuid contents/stability test, by design.

## W3 — per-user Windows fallback remains deferred

- **Decision and candidate API:** do not ship a Windows fallback on the strength of a directory name or an unverified ACL. For a future ordinary-user desktop design, investigate `SHGetKnownFolderPath` from `<shlobj_core.h>` with `FOLDERID_LocalAppData` from `<knownfolders.h>` ([Microsoft sample](https://learn.microsoft.com/en-us/samples/microsoft/xbox-gdk-samples/localstorage/)), `BCryptGenRandom` from `<bcrypt.h>` ([documentation](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptgenrandom)), and wide-character `CreateFileW` from `<fileapi.h>` ([documentation](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)). An explicit user-bound security descriptor, sharing/locking and atomic creation protocol still need design and native review. These APIs are candidates, not a completed implementation.
- **Privacy and stability:** a random per-user app-scoped installation secret may avoid collecting firmware, but is still a persistent correlator. Cloning or restoring a profile may duplicate it; deletion, profile loss, reinstall or changing accounts may change it. It is not device or person authentication and is not permission to circumvent platform fingerprinting restrictions.
- **Permissions, failures and race boundary:** require a standard user without elevation, fail closed on RNG, ACL/owner, reparse, locking, malformed, partial-write, flush or access failures, and specify behavior on ambiguous commit/crash before supporting it. Windows default file ACLs can be inherited; `FILE_FLAG_OPEN_REPARSE_POINT` affects the opened reparse point, not a proof that every ancestor is trusted or race-free. Path ancestry, junctions, hard links, inherited/explicit DACLs, directory replacement and malicious same-user processes need a concrete threat model and tests. File and OS calls have no demonstrated absolute deadline. Do not silently regenerate an existing corrupt identifier.
- **Alternatives:** an unrestricted machine-wide file, bare registry value, administrator-owned location, serial-derived value or default/inherited ACL alone does not establish per-user protection. User-scoped DPAPI (`<dpapi.h>`, [CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata)) may be researched but does not replace ACL/path controls or prevent rollback; Microsoft notes roaming-profile and machine-scope qualifications. No DPAPI selection or persistence guarantee is made here.
- **Evidence and release limits:** `tests/test_platform.c` and native CI exercise the Windows RNG primitive, **not** a Windows fallback. There is no Windows fallback implementation, failure fixture, profile-clone study, standard-user persistence test, Windows 11/client support or Store decision. #4/#6/#30 retain that implementation work.

## M1 — public IOKit research, product collection withheld

- **API/headers and sources:** public IOKit interfaces in `<IOKit/IOKitLib.h>` can locate services and copy a registry property through [`IORegistryEntryCreateCFProperty`](https://developer.apple.com/documentation/iokit/1514293-ioregistryentrycreatecfproperty/). The `Create` result has CoreFoundation ownership obligations; [Apple's ownership guidance](https://developer.apple.com/library/archive/documentation/CoreFoundation/Conceptual/CFMemoryMgmt/Concepts/Ownership.html) describes balancing owned references. Public API availability does not establish a stable contract for a particular property or permission for fingerprinting.
- **Data/privacy/distribution:** the isolated survey transiently obtains platform UUID and serial property objects solely to classify their CF type; it does not read or publish their contents. The product collector is withheld. Apple's [privacy and data use FAQ](https://developer.apple.com/app-store/user-privacy-and-data-use/) and [ad-attribution guidance](https://developer.apple.com/app-store/ad-attribution/) state restrictions on deriving device data to uniquely identify a device under the developer agreement. A host's consent, hashing or technical access does not itself resolve this conflict. Store, signed sandbox, direct distribution and notarization require purpose-specific review of current terms; no legal approval is asserted.
- **Permissions and failure:** nonroot hosted macOS 15 Intel and ARM survey processes observed a platform service and CFString property types; this does not show valid values, sandbox access or physical-device behavior. Null property results cannot reliably distinguish denial from absence. The survey and APIs have no enforced deadline; future collectors must bound resource usage and fail closed on unrecognized types/values and ownership failures.
- **Stability and alternatives:** values can change, be cloned or be virtualized; no authenticity or uniqueness follows. Private API scraping, elevated helper/driver and shell parsing are rejected as substitutes. An app-owned installation value has different scope and still requires purpose/policy review.
- **Tests/evidence:** `tests/test_macos_cf_uuid.c` and `tests/test_uuid_value.c` cover synthetic type, ownership, length, malformed, Unicode and placeholder cases. `tools/permission_survey/native_macos.c` and `tests/test_survey.py` cover the categories-only survey. [Native run 45816632804](https://github.com/archnemix/Archx-RL/actions/runs/45816632804) and the [sanitized survey](../Test-Results/unreleased/native-permission-survey.md) are hosted-runner evidence only. No physical hardware or signed sandbox was tested.

## M2 — macOS per-user fallback remains deferred

- **Decision and candidate API:** do not promote the XDG-oriented POSIX fixture as the product fallback. For a future macOS host, research Foundation `<Foundation/Foundation.h>` `NSFileManager` user-domain `NSApplicationSupportDirectory` ([Apple directory documentation](https://developer.apple.com/documentation/foundation/url/applicationsupportdirectory)) and the host's sandbox/container behavior; [Apple developer guidance](https://developer.apple.com/forums/thread/72813) notes sandboxed Application Support is container-relative. `SecRandomCopyBytes` in `<Security/SecRandom.h>` is already used by the experimental macOS entropy adapter; native file ownership, safe creation, locking, sandbox, entitlement and lifecycle handling remain unimplemented.
- **Privacy/stability:** an app-owned per-user random installation value is potentially linkable, may be copied by backup/clone or changed on reinstall and is not hardware identity. It must not be introduced to evade fingerprinting rules; all intended uses and distribution channels require separate review.
- **Permissions/failure:** no root or bypass entitlement should be assumed. A future implementation must fail closed on RNG, directory ownership/mode, symlink/path race, malformed or partial file, write/flush/lock and permission failures, and must specify crash recovery and user-visible reset behavior. No absolute timeout is demonstrated. Sandboxed versus unsandboxed homes, shared containers, filesystem ACLs, adversarial same-user access and backup/restore need explicit threat-model and implementation review.
- **Tests/evidence:** `tests/platform/test_posix_fallback.c` and `tests/test_fallback_faults.c` test the existing *POSIX XDG experiment* with temporary synthetic data, concurrent first use and injected failures; [native platform run 46144559246](https://github.com/archnemix/Archx-RL/actions/runs/46144559246) passed macOS 15 Intel and ARM fixture jobs. These are not tests of an Application Support implementation, a signed sandbox, physical devices or notarization. There is no approved macOS fallback or product.

## Follow-up gates and evidence boundaries

The records above settle what is selected, rejected or deferred for research, and identify evidence rather than claiming that every proposed implementation exists. Windows/macOS native collectors, secure fallback, per-platform core builds/install, native bindings, physical and client-OS studies, failure/timeout behavior, durability, cloning and policy/distribution decisions remain open in their respective product/release issues. A runner success, API name or ADR does not close those gates. Keep synthetic data and sanitized categories in CI; do not publish real identifiers or private keys.
