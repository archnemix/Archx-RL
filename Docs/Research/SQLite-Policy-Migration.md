# Narrow SQLite policy-tightening experiment

This is **not a supported production migration or backup/restore procedure**. It addresses one part of #13 for the private prototype. It does not complete #13: schema upgrades and safe restore/rollback remain unresolved.

`demo/policy_migration.py::tighten_policy` is an explicitly invoked, offline transaction for schema 3 with the same key. It allows quota decreases and adding or tightening an IP soft challenge. Effective IP and device quotas cannot increase; an existing soft challenge cannot be removed or raised. Window/history durations, selected signals, normalization, IP storage, matching and all other policy semantics cannot change. Message-only differences are already omitted from the stored policy digest and do not require a migration. It preserves windows, observations, signal tokens and replay records, while atomically replacing the policy check. New code rechecks schema, key and policy metadata after acquiring each engine writer transaction; stale engine instances fail closed rather than writing with the prior policy. Restart with the original policy fails, and the reverse transition to weaker limits is rejected.

## Operator boundary

This API is not automatic and has no command-line entrypoint. A controlled experiment creates an `SQLiteEngine` with the existing key/policy and calls `tighten_policy(engine, new_policy)`, then constructs a fresh engine with the new policy. Stop and drain **all** writers and hosts before doing so. Older binaries do not perform the per-transaction metadata check, and replay-store operations do not use that check. All must remain stopped until the operator has replaced them and reviewed the policy; a mixed-version deployment is unsafe. The database directory and all files must remain private and controlled. Do not mutate an engine's settings or secret while it is in use. Per-transaction checks detect selected metadata mismatches and accidental local mutation, not arbitrary file replacement, an earlier valid database, database-content tampering, secret theft, untrusted local users, or clock manipulation. A database operation can block, and an ambiguous commit or I/O failure may require inspection. SQLite durability still depends on the filesystem and configuration.

The transaction does not create a backup and **does not make restoring one safe**. An older copy can omit later charges or resurrect consumed replay challenges; even restoring a copy of the old policy can silently bypass newer usage. Never treat restoring an older snapshot as a safe rollback. Proper rollback needs a supported recovery protocol, prevention or explicit management of lost writes, replay handling, clock and downtime guarantees, tested backup/restore, and owner review. No such protocol exists here. A policy tightening itself can deny additional legitimate users; operators must choose the target and communication plan.

## Historical schema distinction

Schema 2 and 3 use different token derivation and input handling. In historical commit `7ad21f1`, schema 3 introduced domain-separated `archx-raw-v2` HMACs and raw-signal normalization in place of schema 2's caller-supplied hashes. Existing pseudonymous keys cannot be transformed into the new keys without original inputs. Relabeling schema 2 as 3 or simply changing its policy marker would silently orphan active limits and observations. Both schema-2 upgrade and reversible key/token migration require a separate design; this experiment rejects them.

## Evidence and limitations

`tests/test_sqlite_policy_migration.py` exercises preserved quota/history/replay rows, stricter policy after restart, stale writer rejection, reverse/unsafe policy rejection, mutation detection, transactional rollback after an injected update failure, and a migration waiting behind a real SQLite writer. This is synthetic local evidence, not crash-consistency, multi-host, availability, secrecy, or production certification. The normal regression suite includes these tests.
