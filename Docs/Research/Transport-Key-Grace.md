# Experimental sealed transport key grace

This is **not production key management** and only addresses the transport-key part of #12. Pseudonym-key rotation, migration of active limits, durable key management and rollback-resistant restore remain unresolved; #12 remains open. No protocol or cryptographic review has been performed.

`demo/sealed_payload.py` includes an experimental `sealed-v3` envelope and bounded `TransportKeyRing` for a host that explicitly constructs a `RequestService` with that ring and a replay store. A host independently authenticates the pair `(key_id, public_key)` and supplies both to `seal_v3`; the receiver selects one of at most eight configured private keys by the public key ID. The decrypted plaintext includes a domain-separated version prefix and the key ID, so modifying the outer key ID cannot redirect a valid ciphertext, even if two names refer to the same key. The envelope, key ID and length are visible; raw request body confidentiality requires a correctly authenticated key and intact client code. All malformed, unknown-key and wrong-key envelopes produce the same generic invalid-request result, though timing is not guaranteed to be constant.

A controlled synthetic transition can restart with `old` only, then a ring containing `old` and `new` for grace, then `new` only. Existing pending challenges and quotas remain in the same independent SQLite database using the **same** pseudonym/replay secret. Removing a key rejects envelopes addressed to it. Explicitly returning to an old-only ring does not roll back that database; it also rejects new-key clients, so an operator must coordinate public-key distribution and client behavior. The key ring is a copied static mapping in memory, not an automatic rollover mechanism, persistent secret store or lifecycle service. Create a fresh service with an explicitly configured ring; do not mutate service settings or key objects while handling requests. Never log private keys or treat synthetic fixture keys as real secrets.

The existing server command, Python CLI and synthetic demo UI remain **sealed-v2 only**. V3 server setup requires a host wiring the Python API. The browser module can explicitly use v3 when the embedding host supplies both a trusted `keyId` and its public key; omitting `keyId` chooses v2. The module refuses a mismatched server protocol instead of falling back. No backwards-compatible v2-to-v3 live migration or secure public-key distribution is implemented. Sealed boxes are not sender authentication, do not replace TLS and do not prevent an attacker with a public key creating requests. Replay protection is separate, first-arrival-wins and depends on persistent storage. Older database snapshots can resurrect consumed challenges and lose quotas; this experiment does not make restores, service compromise, key theft, clock changes, or pseudonym-secret changes safe. Key rotation can disrupt clients and operators must control retiring keys and the grace duration.

`tests/test_transport_key_rotation.py` uses synthetic keys and an actual SQLite-backed service to test old/new grace, restart, retained replay consumption and quotas, key removal and explicit old-only rollback. It verifies ciphertext key-ID binding, strict input limits, generic invalid results and v2/v3 separation. A concurrent synthetic test sends the same nonce encrypted under old and new keys through separate service instances sharing SQLite; exactly one succeeds, all requests charge the same IP quota, and restart does not resurrect the nonce. `tests/test_browser.py` additionally runs the browser module against a real Python v3 service in both Node and Chromium, including replay and tampered key-ID rejection in Node. These cases are optional without PyNaCl/browser dependencies and required in Linux CI. This is finite synthetic functional evidence, not a proof of production safety, cryptographic correctness, fault-tolerant key distribution or secure memory erasure.
