# Historical analyzer investigation: missing original diagnostic

Issue #22 gives the file and line only, not the diagnostic, flags, compiler or source revision. The initial repository revision `87e4a30` happens to put `memcpy(heap, stack_buf, n + 1)` in `emit_json` on `src/archx.c:263`, and the SHA schedule expression on `src/sha256.c:31`. This coincidence does **not** establish that it is the source revision that produced the reported warning. `git show 87e4a30:src/archx.c` reveals that the old `emit_json` used `strlen(stack_buf)` and ignored its `stack_len`; it allocated `strlen + 1` and checked allocation before the copy. Without the actual analyzer message and execution trace, the warning cannot be classified as a genuine out-of-bounds access, allocation issue, false positive or anything else.

On this Linux x86-64 runner with GCC 12.2.0, compiling that initial revision's core separately with `-std=c11 -D_POSIX_C_SOURCE=200809L -D_DEFAULT_SOURCE -Wall -Wextra -Wpedantic -fanalyzer -O0` emitted **no core diagnostic**; the SHA unit emitted seven uninitialized-schedule reports. The analyzer's complexity cutoffs and compiler-dependent behavior mean that a non-reproduction is not proof of safety, nor a minimized reproducer. See [the main triage](Analyzer-Triage.md) for commands and the SHA rationale.

In the current code, `emit_json` locates a NUL with `memchr` bounded by `stack_len`, denies an unterminated buffer and copies only the bounded length plus NUL. Append and format failures are propagated rather than publishing a truncated result. `tests/test_output_faults.c` uses an unterminated three-byte buffer, exact output boundaries and injected allocation/format failures; the sanitizer suite passes. These changes address independent bounded-output concerns but are not proof of the unspecified historical warning's cause. A maintainer must provide the original compiler, flags, source revision and full diagnostic/trace to classify or reproduce it; no broad suppression was added. #22 remains open.
