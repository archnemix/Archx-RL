# Distributed quota and replay milestone: requirements, not an implementation

This document narrows #17. There is **no distributed backend in this repository**, no selected provider, capacity budget, funding commitment or operational support. SQLite coordinates only processes on one host and must not be placed on a shared/network filesystem and advertised as distributed enforcement. Self-reported device signals are neither authentication nor proof of identity.

## Proposed safety contract

A future deployment needs one logically authoritative, linearizable state machine per enforcement domain, durable across acknowledged leader failover, and a fenced writer epoch. All operations touching one enforcement decision—including every applicable quota bucket and replay state—must be atomic as a unit, or the design must explicitly prove how an alternative sequence preserves the same safety properties. Independent per-key transactions, asynchronous local caches and eventually consistent replicas cannot provide this contract. Cross-shard requests require a proven atomic transaction or co-location with a documented bound; partial charges or nonce consumption must never be mistaken for an allow.

The authenticated host supplies the principal, trusted peer and policy; clients do not choose a principal or internal pseudonym key. A request includes a host-generated operation ID bound to the canonical operation, policy/key epoch and authenticated scope. A durable receipt deduplicates retries: the same ID and same canonical request yields the original result without a second charge; the same ID with different input is denied. Receipt retention must cover the entire maximum retry horizon and any earlier receipt eviction must fail closed, not silently admit a repeat. The design must explicitly choose whether a denied attempt is charged, how soft challenges interact with hard limits, and whether a consumed challenge and final quota decision commit in one transaction. Existing single-host behavior cannot be assumed to transfer unchanged.

For replay, issue and consume an unpredictable, short-lived nonce bound to the intended peer/scope. Issue, expiry and consume are authoritative state transitions; concurrent attempts have at most one winner. Receipt replay must not permit a completed protected operation to execute twice: a stored authorization result is not itself idempotency for an external business transaction. The host must independently make the protected operation idempotent or bind its commit to an appropriate transactional outbox/fencing protocol.

On timeout, network partition, failed quorum, uncertain commit, incompatible policy/key epoch, clock uncertainty, storage capacity or corrupted state, **deny/unavailable**; do not fall back to local independent counters. A client timeout is not proof that a transaction rolled back. Retry only with the same operation ID and canonical inputs. A restored snapshot may be stale even when internally consistent; recovery needs a durable external epoch/fencing mechanism and a method to preserve or conservatively block all post-snapshot quota and replay state. A stale leader, restored node, or process with an older epoch must not issue authorizations. No external epoch mechanism is implemented here.

Time is a security dependency: expiration must not occur early during clock jumps, lease loss or failover. Specify an authority, maximum clock error and behavior when that bound cannot be demonstrated. Treat wall-clock rollback and replay of old state as faults. A request that cannot be safely classified must fail closed. Retention and key rotation require explicit epoch compatibility and must not orphan live quotas or active deduplication receipts. HMAC pseudonyms, payloads and receipts may be sensitive; use least-privilege transport/authentication, encryption, restricted logging and documented deletion. These controls do not make forgeable client signals trustworthy.

## Implementation and acceptance work still required

1. Select and fund a specific consensus/transactional backend, deployment topology, failure model, maintenance ownership, data retention, threat model and recovery targets; no backend or SLO is endorsed here.
2. Implement bounded admission, transactional quota/replay/receipt state, key and policy epochs, authenticated operators, monitoring, restore/fencing and fail-closed adapters. Define a versioned API and migration/rollback strategy before exposing a supported profile.
3. Use real multi-process/multi-node tests with deterministic history recording and a linearizability checker. Exercise simultaneous charges on multiple buckets, issue/consume races, ID reuse with different inputs, expiry boundaries and stale clocks, capacity exhaustion, dropped requests/responses, duplicate delivery, retries after ambiguous commits, leader loss, minority/majority partitions, split-brain fencing, recovery and stale backup restore. Verify no acknowledged charge or consumed nonce disappears under the specified failure model and no external business operation is accidentally executed twice.
4. Run representative sustained contention, churn and failover tests against agreed resource budgets, plus security, privacy, dependency and operational reviews. Synthetic models and a dependency declaration alone cannot satisfy these tests.

These are proposed requirements, not a claim that the current single-host service supplies any distributed guarantee. #17 remains open until an implementation and real failure evidence meet an agreed specification.
