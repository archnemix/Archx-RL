# Windows research: experimental SMBIOS collector

## Decision and boundaries

This is a partial implementation, not a supported Windows release. The internal desktop-only `signals_windows.c` queries `GetSystemFirmwareTable` (`<windows.h>`, `<sysinfoapi.h>`) with the documented `RSMB` provider, using a size query followed by a bounded (1 MiB maximum) read. It rejects changes between query/read and clears the temporary raw buffer. `smbios.c` parses a bounded `RawSMBIOSData` header and Type 1 structures into internal, transient firmware UUID and system serial evidence; no public ABI, fallback persistence, Windows DLL/static library, CLI or Python/Node binding is implemented. The synthetic provider tests and availability-only OS call ran on a hosted Windows Server 2022 x64 runner; a hosted runner is not Windows 11, physical-device or standard-user permission evidence.

Successful OS access does not establish uniqueness, authenticity, stability, entropy, consent or safe use. Firmware identifiers may be missing, placeholders, cloned, spoofed or replaced through servicing or virtualization. Returned raw values are sensitive; the synthetic tests never print them, and the native availability smoke prints only a status then clears its result. The caller must decide whether collection is permitted and protect any transient data; this is not stealth collection, authentication or attestation. User-versus-service context and opt-in/privacy policy are not yet implemented.

## Parser and failure policy

The parser checks the eight-byte Windows header, declared table length, per-record formatted lengths, double-null-terminated string sets, string indices, duplicate Type 1 records, a Type 127 end marker, bounds and zero padding. It rejects malformed or truncated tables as a whole. A missing Type 1, unsupported UUID field, all-zero/all-FF UUID, and invalid/placeholder serial are separately represented; invalid string indices are malformed input. Serial values are trimmed, ASCII-lowercased and limited to 128 printable ASCII characters; non-ASCII and control characters are marked invalid rather than silently coerced. This conservative policy can exclude legitimate vendor values and requires further privacy/normalization review. The parser is not yet a versioned public capability schema.

For SMBIOS 2.6 and later, the first three UUID fields are reordered from SMBIOS wire form; for earlier versions, bytes are displayed in source order as a compatibility heuristic, not a guaranteed universal rule for old firmware. `GetSystemFirmwareTable` errors are classified as denied, unsupported or read error; changing buffer sizes, malformed data and allocation failures fail closed. There is no timeout or asynchronous cancellation on this local OS API. MachineGuid is intentionally not collected; it requires a separate research decision. WMI/CIM and command-line collectors were not selected for this initial raw-table experiment.

## Sources and evidence

Accessed 2026-11-22: Microsoft's [`GetSystemFirmwareTable`](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-getsystemfirmwaretable) documents RSMB, the size-query pattern and `RawSMBIOSData`; its UWP restrictions do not establish desktop or Store compatibility. The DMTF [SMBIOS 3.8 specification](https://www.dmtf.org/sites/default/files/standards/documents/DSP0134_3.8.0.pdf) specifies record bounds, double-null string sets and Type 1 fields; the [2.6.1 specification](https://www.dmtf.org/sites/default/files/standards/documents/DSP0134_2.6.1.pdf) clarifies UUID field byte order. Pre-2.6 handling remains empirical/uncertain.

`tests/test_smbios.c` contains synthetic version, serial, placeholder, truncation, duplicate and malformed-table fixtures and deterministic mutation smoke; `tests/fuzz_smbios.c` provides a coverage-guided target, not proof against every malformed input. `tests/test_windows_firmware.c` injects synthetic API responses for success, denial, unsupported, oversize, changing and malformed tables and performs an availability-only native API call. [Native CI run 45667025930](https://github.com/archnemix/Archx-RL/actions/runs/45667025930) passed the Windows Server 2022 x64 provider/availability test and parser fixtures on Windows and macOS 15 Intel/ARM. [Linux CI run 45667025952](https://github.com/archnemix/Archx-RL/actions/runs/45667025952) passed full regression, a five-second coverage-guided fuzz smoke, and GCC/Clang install tests. The Windows availability status itself could not be retrieved because hosted job logs were inaccessible; the test deliberately permits any documented availability class, so its success does not establish firmware accessibility. No standard-user, service-account, physical machine, VM cloning, sleep/resume, hardware change, signing, Windows 11, release artifact or privacy compliance evidence is yet available. Platform-specific persistence, bindings, full CI and architecture support remain release blockers.
