# Synthetic traffic and state benchmark matrix

Run `python3 tools/traffic_matrix_benchmark.py --requests 20` with `demo/requirements-secure.txt` installed. The [recorded JSON](../Test-Results/unreleased/traffic-matrix.json) reports all 48 cases and the local environment: Linux x86-64, Python 3.11.2, Intel Xeon 2.60 GHz, two visible logical CPUs. This is a sandbox, not agreed reference hardware; **no performance budget or production capacity target is asserted**. Setup/preloading and recovery are outside measured intervals.

The matrix crosses two Python backends (memory and SQLite), three state populations (zero, 31 and 63 preloaded distinct machine signals behind one shared synthetic IP), direct request-service calls and loopback HTTP through the private bounded demo server, and allowed, rate-limited, invalid and sealed traffic. Each engine has a 64-entry capacity; these populations create respectively 0, 32 and 64 IP/device windows before measurement. The empty rate-limited case first makes one successful warmup to exhaust its one-request IP quota; it is therefore not empty when measured. The other rate-limited cases exhaust the IP quota during preload. The sealed case obtains a fresh replay challenge and encrypts every payload; latency and throughput include challenge, client-side encryption and check. Each case makes 20 sequential measured operations (960 total) with one submitted operation outstanding; HTTP sealed operations additionally make 120 local challenge GETs across all sealed HTTP cases. Signals are fabricated and no external endpoint is contacted.

The JSON records per-case outcome counts, exceptions, elapsed time, completed operations/second, p50/p95/p99/max latency, process CPU including client/server/generator, configured listen backlog, handler-start peak active connections, Linux `/proc/net/tcp` listen-queue depth sampled at handler start, and synthetic expiry recovery. Queue depth is a sparse observation, **not** the true maximum: samples can miss bursts, and reading `/proc` adds latency and CPU to the HTTP results. Application, upstream, proxy and network queues are not measured. Peak RSS is the whole process lifetime high-water, including preload and generator, not a per-case delta. For this run, the 48 cases had zero recorded exceptions and all 48 recovered to `allow` after advancing the synthetic clock. The RSS high-water was 28,220 KiB; p99 values ranged from 0.018 to 14.766 ms across the heterogeneous cases. Across 600 handler-start samples, observed listen queue depth was zero; this sequential experiment cannot establish behavior under concurrency or saturation. Refer to individual rows rather than treating this range as a latency guarantee.

`tests/test_traffic_matrix.py` checks category accounting, capacity denial, recovery, matrix coverage, privacy and explicit queue caveats without asserting timing thresholds. The earlier [bounded closed-loop concurrent benchmark](../Test-Results/unreleased/gate-benchmark-memory.json), [SQLite example](../Test-Results/unreleased/gate-benchmark-sqlite.json), [expiry backlog](../Test-Results/unreleased/cleanup-indexed-sqlite.json) and [SQLite multiprocess profile](SQLite-Contention-Profile.md) provide complementary synthetic measurements, not calibrated production workloads.

These tests do not represent real population distributions, open-loop load, remote networks, HTTPS/TLS, a real reverse proxy, multi-host quotas, real identities, provider latency, arbitrary scheduling, long-duration soak or incident recovery. The private demo is not a supported production entrypoint; real deployment analysis needs representative traffic, agreed reference hardware, monitoring and independently agreed budgets.
