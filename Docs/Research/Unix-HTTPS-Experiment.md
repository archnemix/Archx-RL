# Unix-socket HTTPS experiment

This is **not a supported production topology**. It advances #25 and #29 by exercising a real nginx TLS proxy and the separate WSGI enforcement package against a Unix-socket origin rather than the private demo HTTP server. It does not complete those issues: the server, ingress limits, authenticated proxy boundary, identity and operations still need a supported deployment design and review.

On Linux, `ARCHX_TEST_NGINX=/absolute/path/to/nginx ARCHX_TEST_OTHER_USER=nobody python3 tests/test_https_wsgi_unix.py` runs the experiment. Install the test-only `tests/requirements-proxy.txt` and OpenSSL first. The optional other-user check requires noninteractive sudo and a distinct existing unprivileged account. CI explicitly supplies both environment variables; absent nginx skips the experiment, absent other-user skips that particular check, but an explicitly configured missing executable or a failed permission check fails. This uses one nginx worker, a fresh test certificate explicitly trusted by the client, a private Waitress 3.0.2 Unix socket and synthetic-only state. The protected WSGI application uses a fixed synthetic test principal, **not authentication**. Neither the test certificate nor its configuration is for deployment.

Nginx overwrites `X-Forwarded-For` with the direct TCP peer and clears several other forwarding headers; Waitress trusts that field on the Unix socket. Distinct loopback aliases model separate TCP peers. Tests charge one request per peer then send forged single, duplicate, chained or alternate forwarding headers; all are charged to their actual peer and denied. Another peer is admitted. Nginx normalizes/ignores these inputs; the test does not claim it rejects every suspicious HTTP request. A real subprocess running under another unprivileged UID is denied access to the mode-0600 socket. The test directory is traversable for this check while the socket and test private key are owner-only. The full WSGI stack processes those requests, but the scope is one synthetic Linux runner and one configured ingress.

**Critical limitation:** a process running as the service UID can connect directly to the socket and choose any forwarding header; the test explicitly demonstrates two forged peers being allowed. Root or a sufficiently privileged process can also bypass filesystem restrictions. A Unix socket does not authenticate which executable connected to it and its permissions offer no isolation from the service UID. A real deployment needs a defined local threat model, controlled parent directories, dedicated service identities, privilege separation and independently verified permissions and lifecycle; do not infer them from this fixture. Reverse proxies, their workers, filesystem changes, other ingress paths and socket replacement can change the trust boundary.

The experiment configures an 8 KiB nginx body limit and verifies a larger HTTPS request is rejected with 413 before charging the origin; a subsequent valid request succeeds. It also sets a three-second client-body idle timeout and sends a body in nine pieces over more than three seconds, remaining below the idle interval between pieces. The request still succeeds: this is a reproducible negative result showing that an idle timeout alone is **not** an absolute request deadline. This is not a high-concurrency saturation or fairness test and does not prove unbounded memory growth.

The selected nginx/Waitress connection limits and idle timeouts are test parameters, not capacity budgets. They do not establish an absolute deadline for dribbling clients, guarantee bounded upstream/kernel queues, cancel blocked application work or coordinate multiple processes. This test does not establish public TLS/certificate management, all request-smuggling cases, IPv6, multi-hop trust, lossless graceful shutdown, real authentication, safe log policy, or a supported production entrypoint. Continue to keep the demo private and follow [deployment status](../Guides/Deployment.md).
