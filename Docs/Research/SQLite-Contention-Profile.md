# SQLite synthetic mixed-process and fault profile

## Setup and reproducibility

Run `python3 tools/sqlite_soak_profile.py --seconds 30 --nonces 100`; the [recorded aggregate output](../Test-Results/unreleased/sqlite-soak-profile.json) contains the runner environment and worker timing histograms. Each run creates and removes a temporary local SQLite WAL database and uses documentation-only IPs and synthetic values. The test uses a fixed clock, the same hot IP/device, one quota of 100, four independent writer processes, two tight-loop read-only processes, two competing replay consumers and a ninth process injecting read-only storage failures. All processes synchronize at startup. Each writer checks for 30 seconds; replay consumers both attempt each of 100 tokens staggered across the interval. A separate read transaction deliberately pins an old WAL snapshot throughout the workload. This aggressive open-loop loop and pinned reader are stress assumptions, not a representation of normal traffic.

The engine opens a fresh SQLite connection for each request; readers and replay also open one per operation. Therefore wall times include connection churn, transaction acquisition, work and close; this does not isolate connection setup cost. Worker process CPU and per-worker p50/p95/p99/max end-to-end times, plus fixed writer `BEGIN IMMEDIATE` wait histograms, are recorded. They are not independent latency samples from a controlled arrival process. The pinned reader and writer contention can grow WAL and cause high tail latency; this is not a supported throughput or timeout budget.

## Results and invariants

On the recorded Linux x86-64/Python 3.11.2/SQLite 3.40.1 run, writers attempted 17,747 checks in 30 seconds: 100 allowed and 17,647 rate-limited, with each of two quota counters exactly 17,747. Readers completed 243,330 read-only aggregate queries. For each of 100 nonces, exactly one of the competing replay consumers succeeded and one was rejected. A separate nonce survived 297 simulated read-only storage failures and was consumed exactly once after recovery. The failing worker returned 297 `storage_error` and 297 `ReplayUnavailable` outcomes; it did not turn a storage failure into an allow or a successful consume. These are measured invariants in this experiment, not a universal proof under all faults.

Per-writer end-to-end p95 was 7.271–8.462 ms, p99 39.321–109.954 ms and maximum 2,144.806–3,149.570 ms; replay-consumer p95 was 335.409–636.253 ms. Full per-worker times, process CPU and fixed serialization-wait buckets are in the report. Attempts churn connections; replay timing also includes writer contention. Actual timing and scheduling vary substantially across hosts, runs and data.

At the end of the pinned snapshot, WAL size was 75,330,112 bytes. Passive checkpoint returned `(busy=0, log=18284, checkpointed=0)` while pinned and `(0,18284,18284)` after the read transaction ended. Passive `busy=0` alone did not mean the pinned frames were checkpointed. The queried plans used `windows_start`, `observations_expires`, `signals_lookup`, and `replay_challenges_expiry`. The previous [bounded backlog measurements](../Test-Results/unreleased/cleanup-indexed-sqlite.json) measure cleanup on 5,000 expired windows and observations; they are separate sequential experiments, not this concurrent profile. Earlier transaction-held and writer-wait measurements are in [contention-sqlite.json](../Test-Results/unreleased/contention-sqlite.json).

## Scope and tests

`tests/test_sqlite_soak_profile.py` runs a one-second synthetic CI smoke that checks quota and replay accounting, a read-only failure followed by recovery, and indexed query plans; it does not require any performance threshold. Existing `tests/test_sqlite_engine.py` tests a partially charged transaction followed by a missing-table error and rollback, a busy writer, database loss and connection errors. `tests/test_replay.py` separately exercises schema loss, concurrent replay and restart. The longer experiment uses read-only write failure, not an actual disk-full device, torn write, I/O fault, crashed process, hostile database, rollback or power failure. It is neither a multi-hour reliability soak nor a real deployment, capacity or crash-durability certification; storage behavior depends on filesystem, OS and SQLite configuration. SQLite remains single-host with one writer, a five-second busy timeout that is not a request deadline, and no protection from backup rollback, replacement or deletion. Operators must set up independent monitoring, checkpoints, backups, contention limits and recovery; no latency objective or optimization is claimed.
