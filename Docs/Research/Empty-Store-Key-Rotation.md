# Offline empty-store pseudonym-key rotation experiment

This is narrow work toward #12, **not a production key manager, online rotation, active-state migration or completion of #12**. HMACs are one-way: without the original inputs, a new key cannot derive the old pseudonyms. Simply changing the key would orphan active quotas and history. `demo/empty_key_rotation.py::rotate_empty_key` therefore refuses to change a schema-3 SQLite prototype's pseudonym/replay secret unless every recognized quota window, observation, signal and replay challenge table is completely empty, including expired rows. It requires exact recognized schema and metadata, checks SQLite integrity and foreign keys, and updates the key check within one writer transaction without deleting or transforming data. Unknown objects or metadata and incomplete replay schema fail closed.

The operator must stop and drain **all** engines, replay stores, adapters and old binaries first; run the existing bounded cleanup APIs until no rows remain; then explicitly call the API with a fresh secret and restart all components using it. New code's writer-time metadata checks reject stale running instances after the change. Older code without those checks is not safe and must never be used concurrently. No assumption is made that waiting for expiration, cleanup, distributing a key, stopping writers or protecting the database is automatic. Retaining the old secret is sensitive and a compromised key must not be reused. Although this operation can be reversed with the old secret only when the new-key store is also fully empty, it is not a general rollback: it rejects rather than silently losing new-key state.

The stored check is not an external freshness marker or authenticated backup. A stale copy or file replacement can still lose charges or resurrect challenges; **never restore an older snapshot as a rotation rollback**. Mixed versions, a stolen secret, database tampering, malicious local processes, wall-clock changes, lost commits, crash durability, filesystem rollback, and coordinated secret custody/distribution remain unresolved. Database contents and backups may expose pseudonyms and should remain private. The prototype remains unsupported for production. Transport-key grace is a distinct [experiment](Transport-Key-Grace.md), not pseudonym-key grace.

`tests/test_empty_key_rotation.py` covers retained quotas, observations and challenges, expired-but-not-yet-cleaned data, required cleanup, restart under the new key, old-key and stale-writer refusal, refusal to reverse with live new-key state, reversal only after cleanup, incomplete/unknown schema and metadata, injected update denial/transaction rollback, invalid keys, and a writer committing while rotation waits for the SQLite lock. These are local synthetic cases, not a proof of crash safety or multi-host coordination.
