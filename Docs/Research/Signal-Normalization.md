# Synthetic signal normalization and failure policy

Signal values are client-controlled or read from local sources; syntactic validity does not establish origin, uniqueness, stability, or identity. These fixtures use fabricated values, not real device identifiers. Privacy, consent, OS permission, physical/virtual-device availability and production suitability require separate review.

## Linux native C collector

`src/signals_linux.c` collects selected `/etc/machine-id` (falling back to `/var/lib/dbus/machine-id`), DMI `product_uuid` and DMI `board_serial`. A bounded reader gathers a complete first line through EOF or newline, including short reads and interrupted reads. Embedded NUL, overlong first lines, read/close errors and missing files fail closed; the unused remainder of a multi-line file is not used. ASCII leading/trailing whitespace is trimmed and uppercase ASCII is lowercased. Machine IDs must be 32 lowercase hexadecimal characters after normalization, not all zero or all `f`. Product UUIDs must have 36 canonical hex/hyphen characters, not all zero or all `f`; the sysfs source is already a text UUID and **is not** raw SMBIOS wire bytes. Board serials accept 4–128 ASCII characters, starting with a letter/digit and otherwise using letters, digits, space, period, underscore, colon, slash or hyphen, with known OEM placeholder strings and all-zero values rejected. Values outside this conservative subset are marked unreadable rather than silently shortened or coerced; legitimate vendor variants may be excluded.

The new restrictions can change the available signal set or derived identification for installations whose prior collector accepted malformed/non-ASCII/placeholder values. No automatic identity or quota migration is supplied; assess this compatibility and quota impact before upgrade. The fallback machine-id source is used only when the primary is absent or invalid. The system call collector uses synthetic fault and source fixtures in `tests/test_linux_signal_validation.c`; it does not measure real hardware.

## Windows experimental SMBIOS and macOS UUID

`src/smbios.c` parses bounded synthetic RawSMBIOSData Type 1/2 records. On SMBIOS 2.6+ the first three UUID fields are reversed from wire order; pre-2.6 bytes are left in source order as a compatibility heuristic. All-zero/all-FF UUIDs are placeholders; malformed/truncated records reject the entire table. Serial strings are trimmed ASCII spaces, ASCII-lowercased, limited to 128 printable ASCII characters and matched against known placeholders. The SMBIOS parser permits more printable punctuation than the Linux board subset; normalization is not a cross-platform equivalence promise. An absent string index is distinct from malformed or ambiguous records. `tests/test_smbios.c` covers version/byte order, OEM placeholders, invalid Unicode, missing fields, duplicate structures and truncation at every byte; `tests/fuzz_smbios.c` is a bounded smoke target. This parser is not yet wired into a supported Windows product.

`src/uuid_value.c` normalizes exact-length canonical UUID text and distinguishes absent provider data from invalid/placeholder values in the experimental macOS provider. `tests/test_uuid_value.c` and the macOS fixtures cover character/length and provider cases; `Docs/Research/MacOS.md` records platform and policy gaps. No silent claims of cross-platform identity equivalence are made.

## Python raw-v2 service

`demo/signal_validation.py` validates a larger client-submitted set with explicit source formats and a conservative placeholder list. UUID, machine ID, disk, partition, serial, MAC and other formatting rules are specific to each named signal. `tests/test_demo.py::RawSignalTests` covers canonical forms, known placeholders, malformed, non-ASCII and overlength values. Python's client and the Linux C core are separate code paths with different supported fields and normalization rules. Restrictive validation can reject real vendor formats, and passing validation proves only syntax.
