# macOS: CoreFoundation value validation and distribution gate

## Decision, 2026-11-22

This is a preparatory, internal component, **not a macOS collector or platform support**. `macos_cf_uuid.c` accepts a borrowed `CFTypeRef`, checks for `CFString`, bounds the value at exactly 36 UTF-16 code units, and rejects non-ASCII, embedded NUL, malformed or placeholder UUID text. `uuid_value.c` normalizes valid hyphenated UUID text to lower-case ASCII. Both only process values supplied by a caller; neither queries the I/O registry or reads a host identifier. A returned canonical value is not authenticated or guaranteed unique, stable or legally usable. Malformed, missing and placeholder results are distinct; this is not the planned versioned cross-platform signal schema.

Apple's published [user privacy and data use FAQ](https://developer.apple.com/app-store/user-privacy-and-data-use/) says that under its developer program license an app may not derive device data for the purpose of uniquely identifying a device, and its [WWDC privacy-manifest session](https://developer.apple.com/videos/play/wwdc2023/10060/) states fingerprinting is not permitted even with tracking permission. Archx's identification purpose creates a material conflict requiring a specific review of the intended use and current applicable Apple agreements; user consent, hashing, a privacy manifest, or the technical ability to read a value cannot by themselves resolve it. This document is engineering risk assessment, not legal advice or a finding that every use of a UUID is prohibited.

**Distribution boundaries:** Mac App Store distribution is not approved and no compatibility or review claim is made. App Sandbox access/entitlements and privacy manifests have not been assessed in a signed sandboxed app. Direct distribution, including notarized software, requires separate review of applicable developer agreements, law, consent and the actual use; it is not presumed exempt from Apple's terms. Signing/notarization, SDK use in a host app, and browser collection also require separate assessment. Do not integrate or enable a device-fingerprinting collector for these channels until the relevant policy and purpose are reviewed. Independent app-owned random per-user fallback storage is not a license to circumvent these restrictions. An isolated POSIX fallback fixture exercises the Linux-style XDG path with temporary files on native macOS runners; it is not wired into a macOS collector or approved for app distribution, sandboxing or the platform's conventional application-support paths.

## APIs and ownership

The preparatory boundary uses the public CoreFoundation headers `<CoreFoundation/CoreFoundation.h>`: `CFGetTypeID`, `CFStringGetTypeID`, `CFStringGetLength`, and `CFStringGetCharacters`. The caller owns the input; the boundary neither retains nor releases it, and outputs no value for absent, invalid or placeholder inputs. The synthetic macOS tests create owned CFStrings and balance each creation with `CFRelease`. CF implementations and caller-owned objects may retain copies; no secure erasure guarantee is made. The output must be treated as sensitive and must not be logged or persisted raw. `uuid_value.c` requires its input and output not to overlap.

Apple's [CoreFoundation object inspection guidance](https://developer.apple.com/library/archive/documentation/CoreFoundation/Conceptual/CFDesignConcepts/Articles/Inspecting.html) documents using type IDs before casting, and its [memory-management guidance](https://developer.apple.com/library/archive/documentation/CoreFoundation/Conceptual/CFMemoryMgmt/Concepts/Ownership.html) describes Create/Copy ownership. The public [`IORegistryEntryCreateCFProperty`](https://developer.apple.com/documentation/iokit/1514293-ioregistryentrycreatecfproperty/) can return a CF representation, but that fact does not establish that any particular registry class/property is a supported public stable contract or authorized for this product. Research on specific properties, native availability, error mapping and ownership for a collector remains open; no registry access, private API scraping, elevation or driver is introduced here.

## Evidence and remaining questions

Portable synthetic UUID fixtures cover length, separator positions, every byte invalid, embedded NUL, non-ASCII, all-zero/all-FF placeholders, and upper/lowercase canonicalization. Synthetic macOS fixtures exercise CF type, string length, Unicode, NUL, placeholders and reference ownership, without collecting actual identifiers. Local Linux full regression and sanitizer evidence is recorded in `Docs/Test-Results/unreleased/macos-cf-full-test.log`. [Native CI run 45668492708](https://github.com/archnemix/Archx-RL/actions/runs/45668492708) passed synthetic CoreFoundation and portable UUID fixtures on macOS 15 Intel and ARM, plus portable UUID fixtures on Windows Server 2022 x64. [Linux CI run 45668492673](https://github.com/archnemix/Archx-RL/actions/runs/45668492673) passed full regression, fuzz smoke and CMake consumer tests. Synthetic CF tests do not establish real hardware access, sandbox behavior, or release approval. Outstanding: policy/distribution decision, collector APIs with a public documented contract, native permission and stability studies, private per-user fallback, full builds, bindings and signing/notarization.
