# Offline SQLite snapshot experiment

This is partial work toward #13, **not a supported backup/restore or rollback protocol**. `demo/sqlite_snapshot.py::snapshot` takes a SQLiteEngine and publishes a new, private, self-contained snapshot in an operator-owned directory with no group or other permissions. It refuses existing paths and symlinked parent paths, takes a SQLite writer lock and validates the engine's current metadata, uses SQLite's backup API (including committed WAL state), checks integrity and foreign keys, converts the destination to non-WAL mode, checks file ownership and mode, and uses a no-overwrite hard link followed by file/directory synchronization. SQLite and the filesystem can block; there is no bounded-time or crash-durability guarantee.

The operator must stop and drain **all** clients before using it, including old binaries, and control the source, target directory and every ancestor. The lock serializes cooperative SQLite writers during copying but cannot prevent old or new writers from resuming later, filesystem replacement, path races by the service UID, privileged access, tampering, clock changes or an older snapshot being substituted. The snapshot contains pseudonymous security state and must be protected like the live database; it is not encrypted, signed or authenticated and has no external freshness marker. It may become stale immediately after the lock is released. Restoring it can erase later quota charges and resurrect consumed replay tokens. **Never treat a successful snapshot as permission to restore or roll back a live system.** Restore, recovery fencing, backup retention, access control, remote copies, key custody and old-version schema migration remain unresolved.

An error does not necessarily mean that no snapshot was published: if publication succeeded and a later directory sync or transaction operation fails, the destination may exist. Inspect it rather than assuming rollback. A crash or SIGKILL may also leave the private temporary file or SQLite sidecars for careful operator inspection; deletion is not secure erasure. Success does not establish durability on a particular filesystem. Do not copy only the main file of a *live* WAL database.

`tests/test_sqlite_snapshot.py` exercises an actual committed WAL snapshot, retained quota/history/replay rows in a disposable inspection copy, stale replay after later consumption, exclusive publication, pre-existing live-file/symlink protection, unsafe-directory rejection, metadata and publication failures, post-publication sync ambiguity, and a writer committing before a waiting snapshot acquires the lock. These synthetic tests do not validate production restore or real crash recovery. The existing `test_sqlite_restore_risk.py` independently demonstrates unsafe stale restore.
