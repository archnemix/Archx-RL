# Single-process WSGI enforcement integration

`archx_wsgi.ProtectedApplication` is a small WSGI integration for enforcing a host's decision before one protected application. Its supported contract is **application-level, single-process admission and fail-closed decision enforcement**; it is not an HTTP server or a supported production deployment profile. It has no dependency on the demo routes, identity system or a particular gate backend. The repository's synthetic [local example](../../examples/python/packaged_wsgi.py) connects it to the Python `RequestService` without exposing demo routes.

The host must supply all of:

- a real authenticated principal resolver based on trusted host context, **not** a client-controlled HTTP header or self-reported signals;
- an authorization callback that returns the literal boolean `True` for the host-selected, fixed operation;
- an `evaluate(environ, principal)` callback returning a plain dictionary with a `decision`. Only the exact string `allow` invokes the protected application. `invalid`, `challenge`, `rate_limited`, `capacity_exceeded` and `storage_error` map to generic error responses; unknown or malformed results and callback exceptions return 503. Non-boolean authorization results fail closed. Optional integer `retry_after_seconds` in the range 1–86400 is used for 429/503; otherwise retry is one second.
- an HTTP server, upstream proxy and host application with their own reviewed security and lifecycle policy.

The constructor requires finite `max_inflight`, `requests_per_second` and `burst` (token bucket). **All** requests reaching this wrapper, including other methods/routes, authorization failures and gate errors, pass the same local admission before host callbacks. A permitted request holds one in-flight slot through the protected response's iteration and close; overload returns a generic 503. Stalled callbacks, lazy applications or responses whose server never closes them can hold slots indefinitely. Server, host and upstream behavior must follow WSGI's iterable and close contracts. Counts do not coordinate across processes, hosts, independent wrappers or restarts. The wrapper does not create background workers or a queue; it cannot bound the server's accepted sockets, headers, body buffering, kernel/backlog queues, slow clients, TLS handshakes or execution time. Apply independent bounded network controls and deadlines before this layer. The private local example uses `wsgiref` only for illustration and is not that server.

The wrapper itself does not log request bodies, principal data, signal identifiers or exceptions, and its error responses are fixed. Host callbacks, WSGI servers, access logs, proxies, tracing and protected applications can still log or leak sensitive data and must be separately configured and reviewed. The callback must obtain the IP from a correctly isolated trusted transport, bound/validate input and handle any consumed WSGI body before invoking the protected application. Signals remain forgeable and are not authentication. No independent security review, multi-host guarantee or production-readiness claim is made.

Import from this source directory with `PYTHONPATH=integrations/wsgi`, or install the local package with `python -m pip install ./integrations/wsgi`. `0.0.0` is an unreleased packaging placeholder. The local synthetic example's fixed principal is deliberately **not authentication** and it defaults to loopback.

An additional [experimental nginx/Unix ingress candidate](../../Docs/Research/Ingress-Candidate.md) is available for controlled research only. It is not a production profile: its default mode trusts all same-origin-UID processes, while an optional Linux peer-credential experiment trusts all processes with the separate proxy UID. Both modes have significant timeout, queue and operational limitations.

`tests/test_wsgi_package.py` exercises the actual prototype gate, authorization failures, denied/error decisions, generic responses and captured package logs, token/concurrency bounds, mixed routes, lazy-response release and recovery, exceptions, parallel saturation and loopback WSGI. The normal Linux regression runs these tests. These tests are not a slow-client, real-proxy, multi-process or production capacity test. Issue #19 was closed for private single-process overload controls; #25 and #29 remain open until a supported network entrypoint and its topology are established and tested.
