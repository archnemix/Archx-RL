# Device intelligence and anti-abuse: research and Archx assessment

**Research date:** 2026-11-22 UTC  
**Scope:** Linux-native device recognition and account/trial abuse; browser and mobile products are context, not current Archx implementations.  
**Repository examined:** Python demo and C core on branch `arena/328e63a8-archx-rl`; GitHub Linux test run 45047894357.  
**Method:** primary vendor and standards documentation, one academic bot-evasion study, and the repository's code and synthetic test results. Vendor descriptions are claims about their products, not independent proof that they achieve a particular detection rate. Results vary by deployment, threat, user population, and evolving product versions.

## Executive decision

Archx is an early **device-signal correlation and rate-limiting prototype**, not a production anti-fraud or attestation platform. Format validation rejects malformed IDs, but neither a plausible raw ID nor a hash of one demonstrates that the value came from a real device. It is easy to generate a syntactically valid machine ID without owning the associated machine. Changing all reported IDs and the IP defeats the current per-key limits.

**Recommended direction:** retain selected raw-ID submission as the current user-requested experimental mode, with its privacy warnings, but prioritize (1) reliable enforcement at the business action, (2) multi-dimensional and outcome-aware velocity limits, (3) a trusted proxy/TLS boundary, (4) abuse-resistant rate-bucket handling and safe shared storage, (5) measured false-positive and attack testing, and (6) an optional privacy-safer identifier mode after the owner decides the tradeoff. Later consider optional device-key proof of possession and managed-fleet TPM attestation, but do not market either as a universal one-person/one-device guarantee.

**Important conflict with upstream Linux guidance:** systemd says the raw machine ID is confidential and must not be exposed in untrusted environments, particularly on the network; it recommends application-specific derivation instead [1](https://freedesktop.org/software/systemd/man/machine-id.html), [2](https://www.freedesktop.org/software/systemd/man/latest/sd_id128_get_machine.html). The current raw-v2 design was explicitly requested and is not silently changed by this report. Its backend HMAC does **not** undo exposure to the server or TLS termination point. Client-side derivation reduces cross-service exposure but does not stop a modified client from inventing a valid-looking derived value. This is a privacy decision, not a spoofing fix.

## 1. What contemporary systems use

|---|---|---|---|---|

### Vendor and academic evidence, interpreted carefully

* Cloudflare publicly describes heuristic and ML detection using request, session and browser features, with optional JavaScript detection; its bot score is a product-specific likelihood rather than proof of a physical device [1](https://developers.cloudflare.com/bots/concepts/bot-score/). This does **not** mean Archx has comparable models or data.
* AWS ACFP explicitly considers account-creation attempts and aggregates IP/session data; where supported it also considers application success/failure responses. Its documentation says ACFP does **not** evaluate disposable email domains automatically [1](https://docs.aws.amazon.com/waf/latest/developerguide/waf-acfp.html). It is a managed service, not evidence that its exact proprietary rules should be copied.
* The FP-Inconsistent paper analyzed about half a million requests from 20 purchased bot services at a honeysite. Its additional browser inconsistency rules reduced measured evasion relative to two tested services by 48.11% and 44.95%, respectively, in that study [3](https://arxiv.org/abs/2406.07647). Those are **relative improvements in that study**, not accuracy for Archx, native Linux identifiers, real-world signups or future attackers. Privacy browsers and coherent spoofs can change outcomes.
* NIST states fraud indicators do not increase authentication assurance or replace an authentication factor [1](https://pages.nist.gov/800-63-4/sp800-63b.html). WebAuthn/passkeys authenticate control of a credential, not one unique human or physical computer; synced credentials can exist on more than one device. They cannot by themselves prevent a user creating another account.
* W3C's Device Bound Session Credentials draft is intended to reduce export/reuse of session credentials, explicitly not to guarantee a particular device or its state; it designs session keys to avoid a stable cross-session identifier [3](https://www.w3.org/TR/dbsc/). Consider it for future session security, not as a replacement device fingerprint.

## 2. What Archx actually does today

### Python demo

* `demo/client.py` is a native Linux collector, not a browser collector. The browser page is a dashboard and synthetic simulation. The client discovers required/conditional names at `/api/v2/config` and submits selected raw identifiers to `/api/v2/check` after `--confirm-send-raw`; it refuses non-loopback plaintext URLs and redirects. The server itself is plain HTTP and is not a production TLS endpoint.
* `demo/signal_validation.py` normalizes and checks machine IDs, product/partition/filesystem UUID forms, serials, WWNs, NVIDIA GPU UUIDs, MAC addresses and a locally created installation ID. Rules are intentionally a subset and can reject real formats or accept invented but correctly shaped strings.
* `demo/engine.py` hashes normalized values and peer IP with a server HMAC key and uses exact per-signal equality against prior observations. Basic requires `machine_id`, optionally product UUID and board serial, and can relate requests by **any one** selected signal or IP. Standard and Hard require more matching signal names; these are not independent hardware categories, and a required signal must be present but need not itself match. Timezone/IP offset friction is optional and off by default. IP comes from the TCP peer, not untrusted forwarding headers.
* The same fixed-window request threshold applies independently to each supplied signal and IP; malformed requests charge the IP. The `account` field is shape-validated but is not authenticated, used as a rate-limit key, stored as an account-to-device relationship, or connected to actual signup/trial outcomes. A `related` result does not itself deny the request. Therefore the prototype does **not** yet enforce one trial per person/device.
* Memory mode is single-process and volatile. SQLite mode shares state across cooperating processes on one host, using transactions; it fails closed on incompatible policy, secret or schema, storage error or capacity. It is not a distributed multi-host solution. Current observation retention defaults to 86,400 seconds and rate windows to 60 seconds. No production key rotation, retention job or deployment controls exist.
* The C core is separate: app-scoped client-side HMAC profiles and a process-local token bucket with its own APIs. Python raw-v2 policy changes do not automatically apply to C. Neither component implements attestation.

### Measured results and scope

`tools/attack_lab.py` uses deterministic synthetic inputs, not real user traffic. With its 5-per-60-second Basic configuration, same machine/rotating IPs produced 5 allowed and 35 rate-limited; same IP/rotating machines also produced 5/35; rotating both produced **40 allowed, 0 limited**. Two simulated unrelated users sharing one IP under a limit of 1 saw the second limited. SQLite preserved an active limit over restart. These demonstrate behavior of specific scripted cases, **not real-world fraud detection accuracy**.

On GitHub's Ubuntu VM, run [45047894357](https://github.com/archnemix/Archx-RL/actions/runs/45047894357) passed the test suite and saved an availability-only survey in `.github/archx-runner/runs/`. On this VM, both unprivileged users could read machine ID and product UUID, but board/product/chassis serials were root-only and TPM was unavailable/unverified. A VM runner is not evidence of availability on physical laptops, gaming PCs, containers, Flatpak/Snap, or diverse distributions.

## 3. Important gaps and how to address them

### P0 — Business enforcement and trust boundary

1. **Gate the real action.** Integrate the engine with actual signup, trial activation, redemption and login endpoints; ensure all routes (web, API, mobile, partners) use the control. The trusted application must supply the authenticated principal or server-side session and explicit operation/outcome, not an arbitrary account string from the client. Have the service itself atomically enforce trial entitlements with unique business constraints and idempotency keys. A decision and the action must not be separable in a way that allows races or skipping the decision.
2. **Protect the raw-data path.** Terminate modern HTTPS at an authenticated, trusted edge; restrict direct origin access; strip incoming forwarding and risk headers at the edge, then accept them only from configured trusted proxies. Disable request-body logs and debug dumps at every hop, including error monitoring and WAF. Do not send actual IDs to the public HTTP preview. Client consent and endpoint authentication do not protect against a malicious or breached intended service.
3. **Fix attacker-induced collateral damage.** Current limits charge every client-supplied signal before the required-field decision. Someone who knows or guesses another user's valid-looking ID can repeatedly submit it with their own IP and exhaust that signal's bucket. A shared IP can similarly rate-limit innocent users, and shared/placeholder/clone values can poison matching. Preserve the operator's ability to use per-signal limits, but do not rely on an unverified signal alone for irreversible denial; investigate per-source caps, separately scoped combined keys, trusted-key stronger buckets, bounded review/challenge, and monitored recovery. Each has tradeoffs and none verifies a raw ID. Add explicit tests for this exact victim-bucket attack before changing policy.
4. **Capacity and availability.** Distinct attacker-chosen signals/IPs can fill bounded storage; SQLite fails closed while in-memory observation history evicts. Add edge resource limits, per-source quotas for creating new keys, expiry/cleanup, bounded queues, alerts, and an explicit outage/overload policy per operation. Test starvation and failure/recovery. Blindly failing closed can be an attacker-triggered denial of service.
5. **Policy and privacy control.** Display the actual selected signal names and recipient before explicit consent, describe why each is needed, and pin/allowlist the intended service in an embedding application. `--signals` selects enabled optional types but the current `lsblk` invocation requests all four listed storage columns when any storage signal is selected; refine it if strict data minimization is required. A service policy delivered by an authenticated endpoint is still an operator request, not independent proof that collection is necessary.

### P1 — Useful, measurable risk improvements

6. **Per-operation multi-dimensional limits and outcomes.** Separate attempts, successful signups and trial redemptions; short- and longer-horizon counters by trustworthy account/session, peer IP, relevant event and chosen signal. Carefully handle shared networks, sensitive low-entropy contact data and resource-specific limits. A global ceiling is a load-shedding fallback, not a safe proof that every user is abusive. Store keyed, tenant-scoped pseudonyms with clear expiry; never use client-asserted account identity as trusted identity.
7. **More accurate matching without pretending to know identity.** Separate IP evidence from device evidence; group correlated signals (disk serial/WWN/partitions, motherboard/system IDs) and limit the contribution of one family. Distinguish `missing`, `same`, `changed`, `invalid` and unknown rather than awarding nonexistent evidence. Any fuzzy matching should be reversible, bounded, explainable and initially advisory; do not merge accounts permanently on a single low-quality or attacker-supplied value. Required means presence today, so expose match-versus-presence semantics clearly.
8. **Controlled actions and recovery.** Add observe-only, allow, delay, challenge, review and block as explicit operator choices, with reason codes, timeouts, accessibility alternatives, appeal/support and manual reversal. The current timezone result says `challenge` but does not implement a complete challenge flow. A new device, VM, privacy configuration or VPN is not itself proof of fraud.
9. **Shared state and correct time semantics.** For multi-host deployments, evaluate a supported shared transactional service or a carefully designed atomic Redis implementation, with TTL, persistence/recovery and operations testing. Redis Cluster multi-key atomicity requires appropriate key placement or another design; do not assume a single script is atomic across different hash slots. Compare sliding window/log or token bucket against the current first-request-anchored fixed window, which permits boundary bursts. Use trusted time, define timeout/fail-open/fail-closed and test retries and partitions. Choosing Redis alone does not guarantee durability or fairness.
10. **Privacy lifecycle.** Per-service/tenant secret separation, documented key rotation/migration, TTL and deletion for observations/backups, least-privilege access and incident handling. HMACs remain linkable pseudonymous data; predictable IDs can be tested if the key is compromised. Consult counsel for the intended jurisdictions: for example, the UK's ICO says rules can apply to fingerprinting that accesses information on terminal equipment and circumstances matter [1](https://ico.org.uk/for-organisations/direct-marketing-and-privacy-and-electronic-communications/guidance-on-the-use-of-storage-and-access-technologies/what-are-storage-and-access-technologies/). Consent wording alone is not proof of legal compliance.

### P2 — Stronger proofs, where justified

11. **Credential proof of possession.** After trusted enrollment, let a client sign a one-time server challenge and a canonical request digest using a per-service key. Verify signature, intended service/action, nonce, expiry and single-use state server-side; test replay, modification, concurrency, rotation and loss. A software key proves control of that key, not genuine hardware, a clean process, or unique person/device. Enrollment of unlimited new keys is still a Sybil bypass; keys can be copied or used as signing oracles. Nonce-only protection on unsigned raw identifiers does not authenticate their origin.
12. **Optional TPM/Keylime investigation for managed fleets only.** Establish trusted enrollment, manufacturer EK/certificate checks where applicable, AK-to-TPM binding/credential activation, fresh nonce-bound quote verification, PCR/event-log validation against managed reference policies and appropriate revocation. Avoid treating a self-reported TPM flag or an arbitrary signed public key as attestation. Protect privacy of stable hardware credentials. Missing TPMs, restricted access, firmware updates, virtual TPMs and diverse Linux builds require a fallback. Quotes can be relayed from another genuine platform, and measurements do not prove a user is unique or a runtime is free of compromise [5](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/10/html/security_hardening/ensuring-system-integrity-with-keylime), [2](https://www.usenix.org/legacyurl/bootstrapping-trust-trusted-platform). Use maintained attestation software rather than homegrown cryptography.
13. **Future mobile adapters, not Linux substitutes.** Android Play Integrity can bind verdicts to request content and recommends server-side verification and tiered enforcement [1](https://developer.android.com/google/play/integrity/overview). Apple App Attest verifies an attested app key and signed assertions with a server challenge; Apple notes unsupported devices and outages need handling [1](https://developer.apple.com/videos/play/wwdc2021/10244/). They differ in properties and platform dependence; neither proves one person, prevents relays, or covers Linux.

### Do not implement now

* **A magic client secret, obfuscation or self-check** as proof the official client ran: an attacker controlling the client can extract or disable it. Server-side signed challenges only add meaningful authentication when bound to a securely enrolled key, and then prove key possession, not raw-ID truth.
* **Root access, hidden drivers, process/file surveillance, intrusive anti-debugging or bypassing sandbox protections** to harvest more IDs. They introduce security, privacy and distribution risks without proving provenance; no AV/EDR compatibility claim is justified by the present tests.
* **Hundreds of browser signals or typing/mouse biometrics** merely because commercial products advertise them. The current focus is native Linux; sensitive signals add privacy and accessibility costs and need real benefit, proportionality and review.
* **A fraud ML model or percentage accuracy claim** trained on synthetic labels. There is no representative labeled dataset or independent evaluation; deterministic rules with reason codes and measured outcomes are the responsible first step.
* **Hard blocks for a VPN, shared IP, VM, missing TPM, timezone mismatch or one changed ID.** These are contextual indicators with common legitimate causes.

## 4. Evaluation plan before claiming effectiveness

1. Build a threat-model matrix: single IP/device/account rotation; both rotated; replay; plausible fabrication; stolen/known ID used to exhaust a victim bucket; mass unique-value capacity exhaustion; delayed/low-and-slow requests; malformed requests; proxy-header spoofing; distributed race; replayed action/duplicate redemption; storage outage; clock drift; restart and key rotation.
2. Test legitimate changes and failures: shared NAT and households, cloned images, hardware replacement, disk add/remove, reinstall, multi-user Linux, containers, sandbox restrictions, absent/unreadable IDs, vendors with unsupported serial formats, changing timezone/travel and privacy configurations. Include actual physical devices with permission; GitHub VMs alone cannot characterize the population.
3. Collect lawful, consented and minimized ground truth for **actual business outcomes**. Separate device recognition from fraud classification. Measure pairwise precision/recall and false-match/false-nonmatch where ground truth exists; separately measure prevented verified abuse, legitimate challenge/block rates, appeal/reversal, accessibility, conversion and latency. Report denominators, time windows, populations, confidence intervals and unknown outcomes; never infer maliciousness merely because a user fails a challenge.
4. Start new rules in observe-only mode; compare with a control group when feasible, including delayed outcomes. Evaluate per-signal availability, drift and collision by environment, and monitor population shifts. Test bounded deletion/retention and ensure raw IDs never enter logs, traces, exceptions or backups of this service's own persistent data.
5. Review security externally, conduct realistic multi-host load and chaos tests, supply-chain review and Linux package-distribution/AV false-positive testing before production claims. Record the exact environment and whether tests use synthetic traffic.

## 5. Prioritized implementation sequence and decision gates

| Priority | Proposed work | Done when | Dependencies / decision |
|---|---|---|---|
| P0 | Threat model + request/entitlement integration contract | Document all action routes, trusted identity, atomic entitlement and a negative test that cannot redeem by skipping a check | Need a real host application/desired trial rules |
| P0 | Safe deployment boundary and victim-bucket tests | Synthetic spoof/poison/capacity tests exist; trusted proxy tests, TLS deployment and no-body logging are documented and tested | Define deployment and shared-IP fallback policy |
| P0 | Privacy control and identifier choice | Consent shows recipient/names; selected-only collection; lifecycle and data minimization documented | Owner decides whether raw machine ID is worth departing from systemd advice |
| P1 | Multi-dimensional, outcome-aware rate limits | Atomic attempt/success counters, independently configured windows, idempotency, tests for concurrency, shared IP and rotation | Agree permitted identifiers, thresholds, retention and verified outcomes |
| P1 | Observe/challenge/review workflows and monitoring | Reason codes, recoverability, accessibility path, redacted aggregate metrics, shadow mode | Product UX and operator support required |
| P1 | Real-world dataset and test harness | Diverse, consented Linux environments; published denominator, false-positive and drift methodology | Recruitment, privacy and governance |
| P2 | Shared durable multi-host backend | Explicit consistency/failure semantics, cluster-aware atomicity, saturation and partition tests | Real production scale requirements |
| P2 | Optional proof of possession / managed TPM pilot | Documented trust chain, server verification, replay and relay limitations, fallback and lifecycle | Managed devices, hardware access, threat model, security review |

No source in this report establishes a universal best method, a bypass-proof device ID, or production readiness for this repository. Each recommendation should be evaluated against the product's actual fraud losses, intended users, legal obligations and operational cost.
